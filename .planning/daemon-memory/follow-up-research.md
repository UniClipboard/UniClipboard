# 后续内存优化研究（2026-10-21）

## 范围与结论

本轮只研究后续方向，不修改已验收的生产实现。当前 PR 为 Desktop #2055 与 Engine #229；先合入 Engine。原100张图片验收保持有效，本轮带 Heaptrack 的进程不作为新的 PSS 性能基准。

进一步降低内存有空间，但尚不能承诺50MiB。补采发现了此前未细分的OpenAPI深拷贝，优先验证它、SQLite连接池与图片字节所有权，然后分析文件映射占用；网络参数和分配器替换排后。

## 当前约60MiB的构成

原100张负载最后15秒的同步采样：PSS 58.53MiB，其中匿名 PSS 26.86MiB、文件映射 PSS 31.67MiB。文件映射包括可执行文件、共享库与其他文件映射；没有逐映射数据前，不能把31.67MiB全部归给二进制代码，也不能当成 Rust 堆。

因此，缩小业务堆不会等比例缩小整个进程。下一次无分析器采样应补采 `smaps`，按可执行文件、动态库、数据库映射和匿名映射汇总实际 PSS。该诊断只输出类别及字节计数，不记录业务文件名、路径或正文。

## 优化版堆采样结果

与100张验收相同的去符号二进制，build-id `c76111ab3e369501c6304c5991f0067683b22907`，另建独立加密资料，10/10图片均确认入库，静置120秒。只在离线解析时加载匹配符号。静置存活堆17.32MiB，按分配调用栈启发式单一归类：

| 类别 | 静置存活堆 MiB | 已确认的主要分配 |
| --- | ---: | --- |
| 剪贴板适配与捕获 | 4.303 | Wayland `pipe_receive` 分配的4MiB缓冲仍存活 |
| HTTP API / WebSocket | 4.288 | 大额栈指向Swagger/OpenAPI对象深拷贝 |
| Iroh / QUIC / 网络 | 4.040 | 其中2.875MiB来自noq Endpoint固定UDP接收缓冲 |
| SQLite / Diesel | 3.325 | lookaside、页缓存与连接相关分配 |
| 日志与诊断 | 0.532 | 宿主队列0.25MiB，其余为Engine诊断等 |
| Tokio / 线程运行时 | 0.430 | 运行时与线程相关对象 |
| redb | 0.155 | 实际存活量远低于可能配置的缓存上限 |
| 调用栈缓存 | 0.094 | 错误回溯相关 |

这次全程堆峰值141.11MiB发生在首次Argon2初始化，其中加密类128.07MiB，不能当成静置或图片处理峰值。Heaptrack有进程内开销；其PSS不与无分析器基准比较。动态库遍历回调采用既有诊断截栈保护，保留分配/释放字节但部分栈不完整。模块类别不等价于引用所有权；静置快照位于负载结束、复制所有者关闭后的额外5秒观察段，与100张验收的统计窗口不同。

原始证据位于本机既有诊断目录的 `optimized-research-10/`，包含 `metadata.json`、`stress/summary.json`、原始/已解析Heaptrack、`attribution.json`、`timeline.json`、官方汇总和火焰图。首次相对符号目录解析未成功，已改用绝对诊断目录离线重新解析；未解析版保留为诊断记录，不用于上表。

## 逐项调查

### 1. SQLite 连接池：首先做单变量对照

Engine 的 `crates/uc-infra-storage/src/db/pool.rs` 中，`build_raw_pool` 和 `open_existing_db_pool` 都使用默认 r2d2 配置，没有显式设置生产连接上限、最少空闲数或页缓存预算。只有脱离原数据库的临时内存池明确设置 `max_size(1)`。

当前 r2d2 0.8.10 默认 `max_size=10`、`min_idle=None`；后者等价于容量上限，意味着连接池会维持10个连接，而非用到时才逐渐扩展至10。每个连接拥有 SQLite 状态，连接数减少有机会同时降低页缓存、schema 与语句缓存开销。

SQLite 的默认建议页缓存约2000KiB，但这是按需使用的预算，不能推导10个连接实际占用约20MiB。应以实际连接的 `SQLITE_DBSTATUS_CACHE_USED`、`SCHEMA_USED`、`STMT_USED` 及堆采样为依据。

建议实验：容量上限10/4/2与空闲下限1逐项对照；随后再独立比较页缓存预算。设置应收敛在同一生产建池入口，使首次创建、数据库恢复/替换、打开已有数据库具有一致策略。临时内存池有自己的语义，不能盲目套用。

验收：并发历史查询、搜索、图片入库、接收入库、资料替换，记录连接等待p95/p99、SQLITE_BUSY、请求超时和捕获延迟。不能只根据空闲场景改成单连接，必须排查嵌套获取连接导致的等待和死锁。

来源：[r2d2默认值](https://docs.rs/r2d2/0.8.10/r2d2/struct.Builder.html)、[SQLite页缓存](https://www.sqlite.org/pragma.html#pragma_cache_size)、[连接内存计数](https://sqlite.org/c3ref/c_dbstatus_options.html)。

### 2. 图片与剪贴板快照：核实共享所有权和释放时机

Desktop 的 `crates/uc-platform/src/clipboard/model.rs` 使用 `Inline(Vec<u8>)`，派生 `Clone` 会复制完整负载。Wayland 的 `protocol/ext.rs` 与 `protocol/wlr.rs` 缓存最后一份 `SystemClipboardSnapshot`，读取请求通过 `cached_snapshot.clone()` 返回；X11 也有类似缓存读取。Wayland 写入时还需要保留能够向其他应用提供粘贴数据的 `active_source`。

这不是看到缓存就能删除：剪贴板数据源可能已经退出，适配器仍须正确提供后续读取和粘贴。应区分捕获缓存、当前系统剪贴板的数据源与业务处理输入，明确每份字节的所有者。候选方案是不可变负载共享（`Arc<[u8]>`或`Bytes`）及任务结束后及时释放；先画出Desktop到Engine的实际转换链，避免只改一个容器却在边界重新复制。

本轮最后一张PNG实际2,952,602字节（约2.816MiB），`pipe_receive` 的几何扩容留下4MiB容量，即约1.184MiB的容量余量。可先比较接收完成时收紧容量与转换为精确大小的共享切片；这比删除有效快照更容易保持语义，但重新分配可能暂时提高峰值，仍需单变量复测。上述余量是堆容量差，不是已证明可降低同等数量PSS的收益。

Engine 的 `crates/uc-infra-content/src/clipboard/representation_cache.rs` 确实在读取时复制 `Vec`，但 `background_blob_worker.rs` 在终态后已经显式 `remove`。这个缓存主要服务处理中状态，配置上限不能直接当作静置占用。进一步缩小上限可能主要增加磁盘访问，而非降低常驻量。

Engine 的 `chunked_transfer.rs` 在压缩无收益或小负载分支使用 `plaintext.to_vec()`，随后另外生成完整密文。局部候选是借用未压缩输入（例如`Cow<[u8]>`），避免一次完整副本；还应检查完整密文输出的扩容次数。它主要影响处理峰值，不能承诺静置收益。

更大范围的流式压缩/加密需评估既有整块输入/输出接口和协议，不作为当前PR的一部分。不得通过明文临时文件换取较低内存。

验收：相同图片尺寸与内容，记录同时存活的大块分配、PSS峰值和入库延迟；覆盖连续复制、当前剪贴板所有者退出、重复读取、自回声去重、接收后再粘贴。共享明文还需明确生命周期与归零责任。

### 3. 网络：先分离固定开销与真实传输缓冲

Engine 的 `crates/uc-infra-p2p/src/network/iroh/node.rs` 使用单一共享 Endpoint，接收流窗口32MiB、发送窗口64MiB，是流量控制预算，不是启动即分配的内存。不能通过两项相加得出网络常驻96MiB。

`blobs.rs` 的 Downloader 已经是 `OnceLock` 延迟创建并复用。无入站下载的样本不能代表双设备收发后的网络内存；反复销毁它还会损失连接复用并重做打洞。

本轮确认网络存活堆4.04MiB，其中2.875MiB由noq 1.3.0的 `RecvState::new` 分配：最大UDP负载×单次接收分段数×批次大小。它是真正的固定接收缓冲，与32MiB流量控制窗口不同。可研究上游支持的接收批次/分段配置，但不能直接缩小应用层窗口来声称回收了这块缓冲，也不应只为内存复制维护一份noq实现。

建议先采集无配对、已配对空闲、首次收发、120秒静置四种状态的同模块存活分配。只有确认缓冲或连接在终态后未释放，才调整生命周期。较小窗口必须另外测局域网吞吐、高RTT和relay，防止以同步速度换静置数字。不能通过默认关闭relay或暂停完整节点实现本次目标。

### 4. 分配器：保留为对照实验

当前100张验收已设置arena上限2和固定128KiB mmap阈值；大块瞬时保留问题已有实测改善。glibc官方说明：显式设置mmap阈值会禁用自适应调整，使其固定。

下一步可在相同合成负载下单独比较arena=1/2、阈值64/128/256KiB，观察系统调用量、处理延迟、峰值和静置PSS。不能把 `mallinfo2` 的arena空闲字节直接作为可从RSS扣掉的数字：这些页可能并未驻留，且未必可以连续归还。

替换mimalloc等分配器属于独立实验：需覆盖Rust与SQLite/Zstd等C依赖的分配路径、跨平台、线程争用和统计口径。上游通用基准不能证明本程序会更省内存。优先修复明确的存活对象或副本，再做替换对照；不增加定时`malloc_trim`。

来源：[glibc参数语义](https://sourceware.org/glibc/manual/latest/html_node/Malloc-Tunable-Parameters.html)、[mimalloc实现与基准说明](https://github.com/microsoft/mimalloc)。

### 5. 新发现：OpenAPI文档持有完整对象并被路由深拷贝

Desktop 的 `crates/uc-webserver/src/api/server.rs:518` 在release下也构建 `ApiDoc::openapi()` 并挂载Swagger。当前utoipa-swagger-ui 7.1.0的 `axum.rs` 将拥有完整OpenAPI对象的闭包交给 `routing::get`；路由克隆会递归克隆schema、字符串和响应结构。本轮HTTP类别4.288MiB中的大额栈集中于这条链。

候选方案：保留现有 `/api-docs/openapi.json` 与Swagger入口，把生成的文档序列化为一个共享的不可变响应，通过共享所有权返回；也可研究延迟生成以减少未访问文档时的占用。应保持ApiDoc为契约的唯一来源，不手工维护另一份JSON，不默认删除release文档路由。需要评估文档本身的序列化大小；不能承诺4.288MiB全部可回收。

验收：生成JSON与既有ApiDoc序列化结果语义相同，Swagger正常加载，debug路由继续受原门控，路由克隆和并发请求不重复持有完整schema树。补测首次访问后静置，避免只把开销推迟到首次查看文档。

## 下一轮实施顺序

1. 堆采样已完成；补采无分析器映射分布，进一步区分31.67MiB文件PSS。
2. OpenAPI共享响应实验，保持现有文档契约与访问能力。
3. SQLite连接池单变量实验，收益、争用与正确性同时验收。
4. 根据分配栈追踪剪贴板大缓冲所有权，优先消除已确认的整块副本。
5. 在真实双设备场景验证网络组件的生命周期及固定UDP接收缓冲取舍。
6. 比较分配器策略；只有收益足够且无性能回退才考虑切换。

每轮只改变一个变量。通过同尺寸100张图片、120秒静置后再做长期运行，不把不同负载轮次拼接为收益百分比。
