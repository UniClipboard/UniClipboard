# 诊断关联与密文历史恢复：失败清单

基线：Desktop e461eea50235f700268b7e6d9bfc2eba413e9378；Engine 403f3a72ff062760635d6c3407ed5591daf957f7。两项均已核对，Decision: accept。

## 修改前的端到端失败场景

1. 同一真实诊断 ZIP 中，按时间、事件字段和 trace/span 匹配原日志与 OTLP。逐条比较顶层白名单关联值。旧版本应显示匹配事件存在但关联值缺失。run_id 必须保留，不能用另一个 SDK Resource 随机 ID 替代其作用域。未批准顶层键不得复制。
2. 在隔离合成资料中先产生密文历史，停止 daemon 后破坏密文，再启动并导出。旧版本应持续报告持久化失败，无法生成新历史。保存破坏前后 SHA-256。

## 通过条件与边界

- 真实双端活动的全部匹配记录逐值保真，包括出现过的 peer_ref、connection_id、path_ref、capture 元数据和来源 run_id。保留 trace/span；额外属性只能来自原 fields 和明确顶层白名单。重启包保留原运行与新运行作用域。
- 确定损坏、无法解析、格式不支持或文件超限：先成功加密新历史，再以单个有界密文证据槽保留旧密文，最后原子写入新历史。大于容量上限的证据只留有界前缀，并报告原大小和裁剪。
- 密钥不可用、会话锁定、未知加密失败与 IO 错误：保留原 history.enc，不隔离、不覆盖，继续报告可重试状态。V3 KeyUnavailable 与确定 InvalidCiphertext 必须在保留类型来源的边界分类。
- 修复后能够重新持久化并在重启后重载。恢复原因、次数及证据裁剪状态放入加密历史，并出现在主动导出的覆盖摘要中。
- 重复损坏不增加无限证据文件，不生成明文旁路、替代文件密钥或用户内容日志。
- 复用 diagnostics_acceptance_run.py。先执行真实故障场景再改 Engine；不新增单元测试。测试侧修改仅作用于自己的隔离资料。
- 每个验收写明源码、命令、ZIP、SHA-256、断言和清理结果。预期失败与通过证据分开。清理失败必须使验收失败。
