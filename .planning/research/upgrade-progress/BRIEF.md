# 本地资料升级进度产品化

日期：2026-09-09。状态：方案梳理，尚未实施。

## 问题与完成标准

原用户日志证明资料升级耗时 147,199 ms 并成功；界面在 45 秒后报错，后台随后运行，
界面却没有恢复连接。升级成功不等于应用已可用。Engine 修复 PR #55 已合并，
本方案解决启动期间的产品反馈、连接恢复及所需 Engine 能力。

完成标准：历史较多的资料升级期间持续显示真实状态；关闭并重开窗口仍能看到当前状态；
完成后自动进入可用界面；失败有明确原因和合适动作；中断后安全恢复；原数据保留。
不把延长一个固定超时当成最终解决方案。

## 产品流程

普通启动保持轻量，不新增欢迎页或升级确认向导。检测到必须升级本地资料时，
进入独立的资料升级视图。与下载新版本、安装程序、更新说明明确区分。

显示标题“正在升级本地资料”、当前步骤、进度、已用时间、可展开的处理记录。
步骤使用稳定的用户概念：检查资料、转换历史内容、转换附件、校验资料、完成准备。
只有实际转换器支持独立统计时才拆出附件步骤，不按内部 journal 的每个状态机械生成步骤。

- 总量可靠时显示当前步骤的已处理量/总量及进度条；未知时显示不定进度。
- 首版不显示整体虚假百分比、固定步骤权重或未经验证的剩余时间。
- 不能将 representation 数量称为历史条数；一条历史可能有多种内容表示。
  显示单位必须来自实际计量口径，或由 Engine 按 entry 聚合后才称“条历史”。
- 某步骤达到 100% 后切换到下一步骤，不宣称整个升级已经完成。
- 转换、校验和后台就绪全部满足后自动进入应用。非必要的搜索重建不阻塞进入；
  使用现有搜索恢复状态展示其暂时限制。
- 关闭窗口只隐藏，后台继续；重新打开先读取快照，再接收更新。
- 首版不提供暂停和任意取消。系统退出/崩溃后的恢复不承诺逐条续传，
  允许重做尚未提交的步骤，明确显示“正在恢复升级”。
- 正在工作不显示“重试”或触发重启。失败后的重试先确认原任务已结束，
  同一 profile 至多一个升级执行者，多窗口共享同一状态。

处理记录是少量结构化产品事件，例如“检查完成”“正在转换内容”“校验完成”。
允许折叠查看已完成步骤和警告摘要；不直接呈现 tracing 原文、路径或内容。
完整诊断仍使用现有导出入口，不默认向远端上传处理数量、标识或用户数据。

## 状态与动作

| 状态 | 显示 | 可用动作 |
| --- | --- | --- |
| 准备启动 | 正在启动 | 隐藏窗口 |
| 升级中/恢复中 | 当前步骤与真实进度 | 隐藏、查看处理记录 |
| 等待解锁 | 可解锁时明确请求密码 | 解锁、导出诊断 |
| 原设备保护材料缺失 | 说明需要原设备资料恢复 | 导出诊断；不反复要求输入无效密码 |
| 较长时间没有进展 | 耗时较长，仍在检查状态 | 继续等待、导出诊断 |
| 已失败/已中断 | 明确原因，保留当前记录 | 按原因重试或恢复 |
| 已就绪 | 自动进入应用 | 正常操作 |

“进展未变化”不等于进程死亡；需要区分进程存活、状态通道存活、业务进展。
不因计数暂时不动自动杀进程，不因单纯心跳一直刷新就宣称升级健康。
可恢复的历史内容警告单独计数；不可读不应冒充转换成功，控制材料错误仍阻止继续。

## Engine 所需支持

升级仍由现有 ProfileStorageUpgrade 完整负责，宿主只调用一次启动，不指挥步骤。
新增的是用户可见的启动任务进度能力，不是扩展遥测接口来暴露内部状态。
既有约束禁止将 journal phase、generation、空间标识或步骤执行接口公开给宿主。

建议在启动前注入只读的产品进度接收器，现有 Engine::start 的默认调用保持兼容。
内部升级负责人产生稳定产品摘要，Engine 仅接线和转发；最终返回仍是完整 Engine 或错误。
正常运行后的事件流不能承担这一任务，因为 Engine::start 返回前升级已经执行完毕。

建议的语义字段（具体 API 命名留到实现设计）：

- 每次尝试的标识与单调序号，用于丢弃迟到更新和区分重试。
- 产品状态、用户可理解的工作类别、可选的已完成量/总量/单位。
- 当前步骤的警告数、恢复提示、最终结果及有限的错误分类。
- 由完整负责人决定的允许动作，不由界面根据英文错误文本猜测。

计数来自实际扫描/转换/校验工作，推进时机明确：已处理并不等于已耐久提交。
重启后从已有耐久记录重建步骤状态，未提交工作允许重新计数，不伪装精确续传。
接收器必须有界、非阻塞，可合并高频计数更新；慢界面和接收器退出不影响事务。
最终状态及步骤结果不可因合并丢失；显示状态不是恢复依据，journal 仍是唯一恢复事实。

密码交互是独立的启动前解锁能力：只在所需密钥确实可由密码恢复时开放。
原系统随机密钥缺失时，密码无法恢复它；禁止删掉保护材料强行绕过。
其输入通道、敏感值生命周期和绑定兼容性需要在 Engine 实现设计中单独验证。

## Desktop 接入建议

建议把现有本地服务拆成“启动控制已可访问”和“业务已就绪”两种状态。
实例锁取得后、Engine::start 之前启动最小本地状态服务；正常业务接口仅在 Engine
完整准备好后开放。不构造半初始化 Engine，不让 GUI 打开数据库或解析升级文件。

优先复用现有本地 HTTP 认证和连接发现，提供启动状态快照及更新，保持同一监听地址。
原有健康检查继续代表业务就绪，不能把“能查询进度”冒充健康；启动查询使用独立路由。
只绑定本机且认证后可读；认证初始化不得依赖待升级数据库或待解锁业务密钥。
正式编码前验证 auth/conn 初始化能提前执行，若存在依赖先在宿主层拆开。

后台保存最新快照和有界步骤摘要，断线后重新查询；快照加序号避免事件订阅竞态。
原进程已死时只展示经过实例身份校验的退出信息，不能将上一次进度当成仍在运行。
正常业务事件桥在就绪后接入；启动状态观察者覆盖就绪前和失败后的整个窗口生命周期。

统一处理前端 12 秒 watchdog、原生 45 秒等待、连接查询和冷启动动作等待。
它们消费同一启动状态，不再各自把升级耗时判为终止失败。仅探测/网络请求本身保留短超时。
失败状态可被新尝试取代；迟到的健康状态必须更新连接并解除旧错误。

## 实施顺序与验收

1. Engine：稳定产品进度摘要、启动前接收器、真实计量与终态，保持一次启动调用。
2. Desktop：提前开放受保护的启动状态，先打通超过 45 秒后仍自动进入应用的最小链路。
3. 界面：阶段进度、处理记录、恢复和失败动作；关闭重开、重试去重完整接入。
4. 解锁：确认启动前密码恢复适用范围，实现真实可恢复错误的交互；不可恢复状态明确提示。

必须覆盖：无需升级、耗时超过 12/45 秒、未知总量、多个内容表示、警告保留、磁盘满、
访问拒绝、正确/错误密码、原系统密钥缺失、GUI 重开、连接掉线、后台异常退出、
每个已有耐久边界中断恢复、升级完成后服务启动失败、多窗口和连续点击重试。

Windows 真机验收使用完整 alpha.5 合成资料和可控密钥，含文本/图片/附件与大数据量；
原用户完整资料在原密钥可用的环境补做升级和重启验收。不能用数据库单项通过替代。
对原用户日志的 147 秒升级场景复现界面等待与自动进入，再检查历史可读和原文件保留。
不新增 CI 配置，沿用用户指定的真机验证方式。
