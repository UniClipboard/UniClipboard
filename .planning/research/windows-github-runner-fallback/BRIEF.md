# Brief：Windows 自建 GitHub Runner 与云端回退

**日期：** 2026-09-20

**状态：** Locked

**实施日期：** 2026-09-20

**研究问题：** 如何让 Windows 构建在线时使用指定真机，不可用时及时改用 GitHub 提供的 Windows 机器？

## 建议

使用 GitHub 官方 Runner，以仓库级专用标签注册为 Windows 后台服务。每次构建先在 GitHub 提供的 Linux 机器上查询 Runner 是否在线且空闲，然后只生成一个 Windows 构建任务：可用时选真机，否则选 `windows-latest`。

## 关键发现

1. `runs-on` 只做精确匹配，不支持“优先 A、不可用改用 B”；直接指向离线 Runner 会等待最长 24 小时。
2. “先查询、后选择”是成熟项目普遍采用的简单方案，可避免同一次检查在两个位置重复执行。
3. Runner 状态接口需要仓库管理只读权限，默认工作流凭据不足；状态凭据应只留在前置选择步骤。
4. 公开 PR 不应直接使用长期存在的自建 Runner。本次只接入手动构建和受信任的发布调用。

## 实施方式

- Runner：GitHub 官方 Windows x64 包，后台服务运行，默认自动升级。
- 隔离：仓库级注册，关闭默认标签，只保留 `uniclipboard-desktop-windows-x64`。
- 选择：仓库内脚本读取在线、忙碌和标签；任何查询错误都选 `windows-latest`。
- 范围：桌面应用 Windows 构建和 Windows CLI 构建。
- 凭据：使用仓库机密项 `WINDOWS_RUNNER_STATUS_TOKEN`，仅在 GitHub 提供的前置任务中使用；检出代码时不保留写入凭据。

## 不采用的方案

- 直接同时写自建和 GitHub 标签：标签是“全部匹配”，不是候选列表，无法回退。
- 同时启动两份相同检查：会浪费资源，并可能产生互相覆盖的结果和制品。
- 自建任务排队后再靠任务超时回退：未获得 Runner 前不会开始计时，不能解决离线等待。
- 自行实现常驻任务队列：复杂度高，且 GitHub 已负责实际任务分配。

## 约束

- 状态查询与任务分配之间存在很短的时间差；若机器恰在选中后离线，GitHub 仍会等待。稳定运行的后台服务将此窗口降到最小，但 GitHub 没有原生的二次改派能力。
- 自建机器不可执行来自不受信任分支的代码。
- 自建机器不能运行仅适用于一次性云机器的工具链清理步骤。
