# Windows 存储升级可靠性研究

日期：2026-09-09

状态：已实施并通过 Windows 原生验证。Engine 修复提交为 `2a298a2c4fab4719e57b0ac53fe1080eaab08abb`；验证使用用户提供的 Windows 机器，没有保留新增 CI 配置。

文中的来源编号对应 [sources.md](sources.md)，附带的 [flush-probe.rs](flush-probe.rs) 可单独运行。

## 建议

在 Engine 的 uc-infra 中完成一个包含三项内容的修复：统一已有普通文件的持久化刷新；使未完成的数据库拆分可从原库重新准备；加入 Windows 原生升级和中断恢复检查。Desktop 保持现有调用方式，仅在 Engine 验证通过后更新固定提交。

不需要新增依赖、权限设置或公开接口。调用方继续只执行 `ProfileStorageUpgrade::ensure_v3()`。

## 证据与边界

- 最新 Windows 日志在北京时间 21:06 完成自动解锁，升级约 1.7 秒后以 `storage` 分类失败。没有底层系统错误码，因此尚不能把现场错误码 5 写成实测事实。
- Engine 提交 `cc0991e6` 的普通文件刷新使用 `File::open(...).sync_all()`。Rust 1.95.0 Windows 标准库的 fsync 直接调用 FlushFileBuffers；微软要求文件句柄具有 GENERIC_WRITE。[S1][S2]
- 同一用户数据库在 Mac 上完成了全部存储转换；这不是 Windows 原生升级、正式激活或重启成功的证据。
- 中断实验已执行：准备完两份数据库快照，仅修改第一个候选数据库，保持原库修订不变，然后重开升级器。现有实现返回 Corrupt。说明半完成拆分的恢复缺口不是推测。
- 当前 Engine 的检查和覆盖率任务都运行在 macos-14；Windows 安装包构建没有执行这组升级测试。
- 研究未读取或记录用户正文、口令或密钥。实验使用合成数据；用户原始包未改动。

## 文件保存方案

### 普通文件

已有文件使用标准库的非截断写入打开方式：

```rust
std::fs::OpenOptions::new()
    .write(true)
    .open(path)?
    .sync_all()?;
```

`.create` 和 `.truncate` 保持默认 false。缺失文件应报错，不能意外创建空文件；已有字节不能被清空。[S3]

建议由 `crates/uc-infra/src/fs/` 下一个窄的内部函数统一实现，例如 `sync_existing_file`。它只处理已经存在、由当前写入流程拥有的普通文件，不处理目录、SQLite 事务、重试或升级阶段。当前 fs 模块未找到这一能力；现有 `FsAtomicPublisher` 是“不覆盖目标的发布”接口，语义不同，不应扩成通用持久化接口。

对已经持有可写文件句柄的调用，继续在原句柄上 sync_all，无需关闭后再打开。已确认需要调整的普通文件调用共 7 处，见 sources.md。

### SQLite 与文件刷新

SQLite 的提交和 WAL 检查点仍由 SQLite 完成，不能以单独刷新主数据库替代事务持久性。现有 VACUUM、journal mode 和检查点顺序应保留并验证。[S5][S6]

仅在独占候选库的整理流程结束后，关闭专用 SQLite 连接，再执行普通文件刷新与候选发布。对仍有运行期 pool 的控制库检查点，不擅自关闭整个 pool 或切换 journal mode。

检查点返回 SQLITE_BUSY 时不得把它当成已完成；需要验证返回的 busy/log/checkpointed 状态，而不是只检查 SQL 是否执行。此处属于控制库流程需要一并确认的边界，不是本次日志已证明的故障。

### 替换、共享权限与目录

继续复用项目已有的同目录临时文件加替换方式：临时文件写完、刷新并关闭后，替换目标；Windows 使用已接入的 MoveFileExW。禁止跨卷复制后删除来代替同卷替换。[S4]

Rust 默认文件共享标志允许读、写和删除共享，应保留，避免新增打开句柄妨碍 SQLite 或重命名。真正的共享冲突和目录访问失败仍须返回明确失败，不按“权限问题”一律吞掉或无限重试。[S7][S8]

目录刷新不能机械替换为普通文件写入打开。Windows 打开目录的规则不同；项目现有 Windows 目录刷新为 no-op，不能据此声称目录项已经具备断电持久性。MoveFileExW 的 WRITE_THROUGH 文档也不能代替整个多文件提交协议的断电验证。[S4][S7]

本次应明确承诺并验证进程中断后的恢复。磁盘/系统断电恢复要通过 Windows 虚拟机断电实验补充证据，不把普通进程退出测试冒充断电测试。

## 未完成拆分的恢复

### 现有缺口

```text
TargetStaged：两份候选都是原始快照，进度保存的是原始摘要
  -> 修改 profile.sqlite
  -> 刷新或进程退出失败
  -> 进度仍为 TargetStaged，但候选字节已改变
  -> 重启按原始摘要校验候选
  -> Corrupt，无法继续
```

仅修正 Windows 刷新方式，不能恢复已经遇到上述失败的资料。

### 推荐规则

只在一次 ensure_v3 调用的恢复入口，持有现有独占锁、确认活动布局还不是 V3、原始资料身份匹配后处理：

1. 如果保存的阶段是 TargetStaged，先检查两份候选是否仍为完整快照；只有缺失或摘要不符才从有效原库重新准备。完整快照直接继续，避免分步执行时反复重置。
2. 先原子保存 Detected 重建计划，复用原计划的候选 generation 标识。
3. 下一步由现有 staging 逻辑幂等清理这组未激活候选，再获取一致快照、拆分和验证。
4. 同一次调用的正常阶段推进不能反复重置，避免恢复循环。
5. 原始资料发生正常修订时，沿用已经实现的来源修订重建规则；原始身份不匹配、无法认证或不兼容仍停止。
6. 已激活 V3 永远不进入上述清理，后续恢复只能向前完成。不能删除原库、历史内容或整个升级目录来掩盖故障。

这是主动放弃低成本且尚未提交的准备副本，重新读取已认证的原始资料。不是忽略摘要错误后继续使用半成品。应同时修订旧文档中“任何 TargetStaged 摘要不符均永久阻断”的说明，明确来源和候选的信任边界。

PrimaryPayloadsConverted 等后续阶段已经使用工作目录和验证边界，保留现有续跑行为；不得把所有阶段无条件归零。对于目录重命名前后进程退出，应补充故障注入，证明恢复确实使用完整输出或从工作阶段重新开始。

## 诊断信息

下次不能再只剩 storage 或 corrupt。由升级流程内部记录失败阶段、固定操作名、io::ErrorKind、可选 raw_os_error，以及候选是否已激活。

保持完整错误来源，但不直接把整条错误字符串写进日志；底层字符串可能含用户路径。不要记录路径、文件名、正文、密码、密钥，也不要为诊断向 Engine 的公开接口泄露内部阶段。实现时遵循现有观测规范并使用模块内部事件。

## 方案取舍

| 方案 | 判断 |
| --- | --- |
| 非截断写入打开，再刷新 | 推荐；标准库已满足需求，覆盖全部普通文件调用 |
| 只改首个报错点 | 不完整；后续还有同类操作，失败现场也需要恢复 |
| 忽略 Windows 的刷新错误 | 拒绝；把保存失败伪装成成功 |
| 改成 sync_data | 拒绝；Rust Windows 实现仍进入同一刷新调用 |
| 要求管理员运行或刷新整个磁盘 | 拒绝；不能修正只读句柄，扩大权限且影响无关资料 |
| 删除用户原始资料或整个升级目录 | 拒绝；破坏恢复事实与资料安全 |
| 新增通用文件框架或重写存储层 | 不需要；现有标准库、windows-sys 和 SQLite 足够 |
| 增加永久快照文件或新的 journal 格式 | 当前不推荐；原库仍为权威来源，重做未提交准备可避免新格式和额外持久副本 |
