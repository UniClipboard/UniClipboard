# ADR-012：CLI 以完整用户流程承接 Engine 能力

- **状态**：已实施
- **日期**：2026-08-18
- **相关决策**：
  - [`ADR-008`](../architecture/adr-008-uniclipd-split-gui-as-client.md)
  - [`ADR-011`](./adr-011-offline-first-member-removal-integration.md)
- **当前 Engine 基线**：`94b21aac9db2fa0fb89bc9027f0e05e545ecc1f5`
- **实施日期**：2026-08-19

## 背景

CLI 已能创建 Space、发出邀请、加入或切换 Space、查看成员和移除成员，但它没有完整承接
Engine 已经公开的三组可操作状态：

1. 加入请求可能长期处于 `pending`，Engine 持久保存当前加入状态，并支持显式取消。CLI
   在本决策实施前只能发起加入并展示本次返回，结束后不能继续查看或取消。
2. Engine 可能要求本机对设备组变化作出决定。桌面 GUI 可以查看并处理，CLI 只能显示
   部分摘要，不能完成决定。
3. Engine 支持读取和修改每个成员的发送、接收与内容类型设置。桌面 GUI 可以管理，CLI
   只能列出或移除成员。

这些缺口在无头节点、远程终端和自动化环境中尤其明显：用户可能可以启动一个动作，却无法
仅通过 CLI 查看并完成该动作。

本 ADR 不要求 CLI 暴露 Engine 的全部内部操作。只承接满足以下条件的能力：它已经由
Engine 拥有、已经通过 daemon 对宿主公开，并且缺少 CLI 入口会使用户流程无法完成。

### 能力核对

| 用户流程                               | Engine 与 daemon 现状                                            | CLI 现状                                                     | 本 ADR 决定                        |
| -------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------- |
| 加入 Space                             | 可返回 `active`、`pending`、`rejected`，可查询当前加入并显式取消 | 只能发起；升级 Engine 后可显示首次结果，但不能继续查看或取消 | 补齐默认等待、立即返回、状态和取消 |
| 处理设备组变化                         | 可查询当前变化、两种决定及各自影响                               | 只能看到成员和移除状态，不能作出决定                         | 补齐查看、应用变化、保留当前设备组 |
| 每成员同步设置                         | 可读取和部分修改发送、接收及内容类型                             | 无入口                                                       | 补齐查看和部分修改                 |
| 成员移除与收敛                         | 已有移除和移除状态命令                                           | 流程完整                                                     | 保持现状                           |
| 邀请、成员列表、发送、接收、搜索和诊断 | 已有对应 CLI 流程                                                | 流程已存在                                                   | 不在本 ADR 重复设计                |

因此，本 ADR 处理的不是所有 Engine 操作与 CLI 命令之间的机械差集，而是三个已经暴露到
daemon、但 CLI 用户在本决策实施前无法完成的流程。Engine 的内部维护、恢复和协议操作继续
保持隐藏。

## 备选方案

### 方案 A：只修复编译兼容，不扩展 CLI 流程

CLI 接受 `active`、`pending`、`rejected` 三种加入结果，但收到 `pending` 后立即结束。

优点：

- 改动最少。
- 不增加新命令。

缺点：

- 用户无法从 CLI 继续查看或取消等待中的加入。
- 无头节点仍需借助 GUI 或直接调用 HTTP。
- CLI 能启动流程却不能完成流程，产品能力不闭环。

### 方案 B：为 Engine 操作逐一增加原始命令

直接按 Engine 操作名暴露查询、取消、决定和设置命令，并要求用户传递 `join_id`、
`change_id` 等标识。

优点：

- 与 Engine 操作一一对应。
- 自动化调用可以精确指定内部对象。

缺点：

- 把 Engine 的协调细节泄漏给用户。
- 用户需要先组合多个查询，再把内部标识传给下一条命令。
- CLI 容易形成独立于 GUI 的第二套业务编排。

### 方案 C：CLI 在本地保存状态并自动编排恢复

CLI 自行记录当前加入或设备变化；发生冲突时自动执行取消、重置、重新加入等动作。

优点：

- 单次命令可以隐藏部分等待和恢复过程。

缺点：

- 产生第二份状态来源，与 Engine 的持久状态竞争。
- CLI 退出、daemon 重启或其他客户端操作后，本地状态容易过期。
- `cancel -> reset -> join` 会改变用户动作语义，并可能破坏身份、历史或恢复材料。

### 方案 D：以用户流程组织命令，状态始终来自 Engine

CLI 提供“加入”“处理设备变化”“管理设备同步”三组完整流程。CLI 可以等待和展示，但不
保存业务状态、不推断结果、不替 Engine 编排恢复。

优点：

- 命令按用户意图组织，内部标识通常无需用户处理。
- GUI、CLI 和其他宿主共享同一份 Engine 状态。
- CLI 中断和重启后仍可恢复观察，不需要本地状态文件。

缺点：

- 需要补齐 daemon Rust 客户端中尚未覆盖的请求。
- 需要定义稳定的终端输出、JSON 输出和退出状态。

## 决策

采用方案 D。

### 1. 所有业务动作仍通过 daemon 到达 Engine

CLI 不直接读取数据库、持久化加入状态或调用 Engine 内部组件。查询、等待、取消和决定都
通过现有 daemon API 完成。daemon API 返回的 Engine 当前状态是唯一事实来源。

CLI 可以保留一个正在显示的快照，但每次状态刷新必须重新读取当前状态，不在本地合并多份
快照，也不从设备在线状态推断业务结果。

### 2. 加入流程使用 `join` 命令组

用户入口为：

```text
uniclip join [现有加入参数]
uniclip join status
uniclip join cancel
```

现有 `uniclip join --code ...`、交互输入和 `--switch` 用法保持不变。`status` 与 `cancel`
作为无加入参数的保留子命令；子命令和加入参数不能混用，避免一条命令同时表达“发起”和
“查看或取消”两种意图。

`uniclip join` 的默认行为是等待本次请求进入 `active` 或 `rejected`：

- 首次 `JoinSpace` 返回 `active`：立即报告完成。
- 首次返回 `rejected`：报告拒绝原因并失败结束。
- 首次返回 `pending`：持续读取 Engine 当前加入状态，直到完成、拒绝或用户停止等待。
- 用户按 `Ctrl-C`：只停止当前 CLI 的等待，不取消 Engine 中的加入请求。
- 用户显式执行 `uniclip join cancel`：取消当前等待中的加入请求。
- 自动化需要立即返回时使用 `--no-wait`；请求被 Engine 接受为 `pending` 后正常结束，并在
  输出中明确标记 `pending`。

默认等待没有固定超时。加入审批和对端上线时间不由本机决定；需要自行控制时间的脚本使用
`--no-wait` 后调用 `join status`。daemon 短暂重启或连接中断时，CLI 可以重新连接并继续
读取同一个加入状态，但不能因此重新发起加入。

等待期间只进行状态查询，不再次调用 `JoinSpace`。CLI 重启后，`uniclip join status` 继续
读取 Engine 保存的当前状态。用户再次执行带加入输入的 `uniclip join` 是新的显式用户动作；
CLI 仍只发起一次 `JoinSpace`，不在客户端拼接取消、重置或重试。

`uniclip join cancel` 先读取当前加入状态，再使用其中的 `join_id` 发起取消。若没有等待中的
加入，显示“当前没有需要取消的加入请求”并正常结束。取消请求与状态读取之间发生变化时，
以 Engine 对 `join_id` 的校验结果为准，CLI 不尝试取消其他请求。

`uniclip status` 只显示一行加入摘要；完整信息由 `uniclip join status` 提供，避免两个命令
分别定义状态含义。

### 3. 设备信任决定进入 `member trust` 命令组

用户入口为：

```text
uniclip member trust status
uniclip member trust apply [--change <change_id>]
uniclip member trust keep [--change <change_id>]
```

- `status` 展示当前变化及其影响，不要求用户提供 `change_id`。
- `apply` 接受 Engine 当前设备组变化。
- `keep` 保留当前设备组。
- 交互模式执行 `apply` 或 `keep` 时，CLI 重新读取当前变化，展示所选结果的实际影响，并以
  “否”为默认值要求确认；提交时使用刚展示的 `change_id`。
- JSON 或其他非交互模式必须显式提供 `--change <change_id>`，不读取终端输入。这样脚本不会
  把针对旧变化的选择应用到后来出现的新变化。
- 如果接受变化会移除本机，还必须提供 `--confirm-local-removal` 或完成单独的交互确认；通用
  `--yes` 不能代替这项确认。
- 没有待决定变化时，三个命令都给出明确的无操作结果；`status` 正常结束，动作命令不伪造
  “已应用”结果。

若变化在展示后、提交前已经改变，Engine 会根据 `change_id` 拒绝旧决定，CLI 重新显示当前
状态并要求用户再次选择，不能自动把原选择转移到新变化。CLI 不根据成员数量、在线状态或
旧快照构造设备信任结论。

### 4. 每成员同步设置进入 `member sync` 命令组

用户入口为：

```text
uniclip member sync show <device>
uniclip member sync set <device> \
  [--send on|off] \
  [--receive on|off] \
  [--send-types <types>] \
  [--receive-types <types>]
```

- `show` 显示该成员当前的发送、接收、发送内容类型和接收内容类型。
- `set` 只修改用户明确提供的设置项，未提供的设置保持不变。
- `set` 至少要求一个设置项；空修改直接提示用法，不发送请求。
- 内容类型接受逗号分隔的 `text`、`image`、`file`、`link`、`rich-text`、
  `code-snippet`，并支持 `all` 和 `none`。CLI 将输入转换为 Engine 已有的内容类型集合，不
  定义新的内容分类。
- 更新成功后重新读取设置，并展示 Engine 实际保存的结果。
- 交互式终端可传无歧义的设备名；名称重复时必须要求设备 ID，不能自行选择。
- JSON 和其他非交互场景必须传设备 ID，并始终返回设备 ID，避免设备改名使脚本指向不同
  成员。

设置的业务含义仍由 Engine 决定。CLI 不把“禁止自动发送”“禁止手动发送”或其他未来策略
自行折叠成一个本地开关。

### 5. 输出和退出规则

人类可读输出说明用户动作、当前状态和下一步，不直接暴露内部错误编号。JSON 输出使用稳定
字段，并保留诊断所需的 `join_id`、`change_id`、设备 ID 和结构化原因。

| 场景                                    | 退出结果                              |
| --------------------------------------- | ------------------------------------- |
| 加入完成                                | 成功                                  |
| 使用 `--no-wait` 且请求已进入 `pending` | 成功，JSON 明确返回 `status: pending` |
| 用户停止等待，但请求仍在继续            | 中断；不得报告取消                    |
| 加入被拒绝                              | 失败                                  |
| `join status` 没有当前请求              | 成功，返回 `status: none`             |
| `join cancel` 没有等待中的请求          | 成功，说明无需取消                    |
| `member trust apply/keep` 没有当前变化  | 失败，提示先查看当前状态              |
| 设备信任变化编号不匹配或已过期          | 失败，返回当前状态并要求重新选择      |
| 同步设置修改后重新读取失败              | 失败；不得只报告“已保存”              |

JSON 模式每条命令只输出一个完整对象，不输出持续刷新的多行对象。默认等待模式在最终状态
到达后输出一次；`--no-wait` 在首次状态返回后输出一次。

新增 JSON 字段沿用现有 CLI 的 `snake_case` 命名。状态值和原因使用稳定的小写标识，不把
面向用户的说明文字当作脚本契约。人类可读模式可以补充下一步提示，但不得改变 JSON 内容。

## 不变量

1. Engine 是加入状态、设备信任状态和成员同步设置的唯一拥有者。
2. 每次显式执行带加入输入的 `uniclip join` 只产生一次 `JoinSpace` 调用。
3. 等待、重连、CLI 重启后继续查看均不产生新的加入动作。
4. `Ctrl-C` 不等于取消；只有 `uniclip join cancel` 表达取消意图。
5. CLI 不实现 `cancel -> reset -> join`、本地重试编排或客户端状态持久化。
6. GUI 与 CLI 可以有不同呈现，但必须读取同一份 Engine 状态并遵守同一动作语义。

## 后果

### 正面

- CLI 用户可以完整完成 Engine 已公开的关键流程，不再需要借助 GUI 或直接调用 HTTP。
- 无头节点和远程终端获得与桌面 GUI 一致的业务能力。
- 中断、重启和多客户端观察不会产生第二份状态来源。
- 内部标识仍可用于 JSON 自动化和诊断，但不成为人工操作的必需知识。

### 代价

- `join` 从一次请求命令变成默认可等待命令，需要处理 daemon 重连和终端中断。
- daemon Rust 客户端需要补齐取消加入、设备信任决定和成员同步设置调用。
- 现有 `join` 参数形式需要与 `status`、`cancel` 子命令共存，并保持旧调用方式可用。
- CLI 帮助、JSON 契约和端到端测试范围扩大。

## 范围外

- 不追求把 Engine 的每个操作都暴露为 CLI 命令。
- 不在 CLI 中实现 Engine 的加入恢复、成员收敛、设备信任或同步策略。
- 不新增 CLI 专用数据库、状态文件或恢复队列。
- 不改变 GUI 的现有交互。
- 不在本 ADR 中定义新的 Engine 操作；若现有 Engine 行为不能满足上述不变量，应先在 Engine
  仓库完成相应决策和实现，再由 desktop 固定新提交。

## 实施顺序

### Engine 基线条件

当前固定版本保证：即使加入事务期间设备信任明细暂时不可读取，已持久保存的当前加入仍通过
公开状态返回，并可按其 `join_id` 取消。因此 CLI 无需保存第二份状态，也不需要读取数据库或
根据网络进度推断加入结果。

发生在建立本地加入记录之前的校验失败，例如口令不匹配，可以直接作为本次命令失败返回；
CLI 不把这类失败伪装成之后仍可查询的 `rejected` 状态。已经进入持久加入流程的拒绝继续由
Engine 的当前加入状态返回。

1. **加入闭环**：补齐状态查询、默认等待、`--no-wait`、取消和稳定输出。
2. **设备信任闭环**：补齐查看影响、应用变化、保留当前设备组和本机移除确认。
3. **成员同步设置闭环**：补齐读取、部分修改和设备选择。

每一步都应先打通“CLI → daemon → Engine → CLI”的最小完整流程，再增加人类可读输出与
JSON 输出。不得先在 CLI 中复制 Engine 状态或规则来模拟完成。

## 验收

- 加入返回 `pending` 后，默认命令继续等待；`Ctrl-C` 后请求仍可由 `join status` 查看。
- `join cancel` 能取消当前等待请求；没有等待请求时不产生误导性错误。
- CLI 重启和 daemon 重启后，状态查看继续以 Engine 当前状态为准。
- 设备信任变化可以完全通过 CLI 查看并作出两种决定，本机移除需要明确确认。
- 每成员同步设置可以查看和部分修改，更新后显示 Engine 实际结果。
- 人类模式和 JSON 模式覆盖 `none`、`pending`、`active`、`rejected`、过期决定、重复设备名
  和设置重新读取失败。
- 真实 daemon 端到端测试证明每个命令只触发预期的一次用户动作；单元测试或仅通过构建不
  作为完整验收。

### 验收结果

本决策已按上述范围实施。真实 daemon 流程覆盖以下结果：

- 加入状态的 `none`、`pending`、`active`，以及加入失败的普通文本和 JSON 输出。
- 默认等待、`Ctrl-C` 只停止等待、CLI 退出后继续查询、daemon 重启后继续查询和显式取消。
- 设备信任状态、过期决定、保留当前设备组、应用变化和本机移除的独立确认。
- 成员同步设置的读取、部分修改、修改后重新读取，以及普通文本和 JSON 输出。

已持久拒绝状态、重复设备名、设置修改成功但重新读取失败和稳定 JSON 字段由可控边界测试
补充。真实 daemon 的请求记录同时证明加入、取消、同步修改和设备信任决定各提交一次，过期
决定和缺少本机移除确认不会提交决定。五条完整流程均通过。Engine 固定提交已发布到远端分支
`fix/current-join-visible-during-transition`，远端提交与本 ADR 记录的基线一致。
