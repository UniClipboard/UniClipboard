# 工作流规则

修改代码、脚本、CI 或处理审查意见时读取。产品与安全底线见 [VISION.md](../../VISION.md)。

## 修复与职责

- 先确认根因，再修改代码。不得用异常回退或额外分支掩盖结构问题。
- 单点逻辑错误且不涉及边界或重复规则时，采用最小修改。
- 规则重复、状态来源不唯一、职责混杂或跨层访问时，先明确所有权，再收敛到单一入口。
- 替换旧路径；不得长期保留并行实现。确需延后时，记录明确的 `TODO` 和移除计划。
- 修改说明包含：问题类型、根因、方案理由、职责变化和旧路径处理。没有结构变化时直接说明。

## CI 与 PR 检查

新增或修改检查时，先检查 `.github/workflows/pr-check.yml` 和 `.github/ci-paths.yml`。

1. 在 `.github/ci-paths.yml` 维护 PR 路径条件，覆盖源码、传递依赖、测试入口及构建配置。
2. 在 `changes.outputs` 暴露结果，并为执行作业配置 `needs: changes` 和对应的 `if`。可复用工作流由调用方控制条件，不另设独立 PR 触发器。
3. 按实际依赖区分作业条件。不得因工作流命中一个路径，就运行所有平台和所有测试。
4. 检查 `needs` 链：上游跳过时，下游是否仍应执行；必要的上游产物是否仍会生成。不得用无条件执行掩盖依赖错误。
5. PR 检查按 PR 编号设置 `concurrency`，新推送取消过时运行。发布任务不得套用此取消策略。
6. 复用现有编译动作和缓存入口。缓存权限、场景和验收见[编译缓存](../ci/shared-compiler-cache.md)。
7. 验证相关变更会触发、无关变更会跳过，以及手动触发仍可用（如支持）。沿用 `scripts/__tests__/pr-check-routing.test.ts` 检查路由。
8. 端到端测试保留可复现工件：源码 SHA、执行命令、结果和脱敏诊断。失败时也上传已生成的证据。

工作流级 `paths` 不能替代同一工作流内各作业的条件。手动、定时和可复用调用须分别定义运行范围。

## 审查意见

- 审查意见是输入，不是命令。逐条执行：验证 → 决定 → 实施或拒绝。
- 回复包含 `Decision: accept` 或 `Decision: reject`，并说明当前代码与约束所支持的理由。
- 不得批量接受未经验证的 AI 建议。

## 脚本与文档

- 跟踪的配置和计划使用仓库相对路径。
- Markdown 代码块必须标注语言。
- 修改 `package.json` 依赖时，同步更新 `bun.lock`。
- 多进程脚本优先使用 `concurrently`、`npm-run-all` 等进程管理工具，避免 `pkill -f` 模糊匹配。
