# 核心诊断与桌面接入

桌面端使用 Engine 提供的本地连接诊断能力。后台服务是唯一采集负责人；图形界面和命令行只通过现有本机认证通道控制和查询，不创建第二份 Engine，也不直接读取后台状态。

## 进程所有权

`uc-bootstrap` 在后台进程启动时安装共同观测运行时，并把唯一控制句柄交还给后台组合根。后台进程负责：

- 登记桌面主进程来源，记录运行开始、结束和所有权释放；
- 启动、停止和查询限时详细记录；
- 导出前刷新 Engine 文件并取得真实覆盖报告；
- 正常退出时结束未完成记录并关闭文件运行时。

桌面主进程目前只能报告自己拥有的运行事实，因此来源能力标为部分支持。后台进程用一个有界、可取消并在退出时等待完成的观察任务检测长时间停止调度；恢复后保守结束仍在运行的详细记录。它只说明进程经历了暂停，不推断具体操作系统原因。

GUI 关闭或进入轻量模式不会影响后台采集。后台重启后产生新的运行编号并回到标准模式，客户端不能恢复或停止旧编号对应的记录。

## 控制入口

后台服务在原有认证保护下提供三个连接诊断入口：

- 查询当前模式、剩余时间、运行编号、来源能力和丢弃情况；
- 请求 1–15 分钟的详细记录，重复请求返回原记录且不延长；
- 使用当前记录编号停止，旧编号不能停止新记录。

设置页显示后台返回的实际状态，本地倒计时只作说明。详细记录期间和后台暂时不可用时，页面定期重新查询；请求响应丢失后也先查询，不盲目重复开启。命令行的 `debug capture` 子命令使用同一后台接口。

## 诊断包

桌面诊断包由 `uc-observability` 统一组装。它只识别固定命名的 GUI、后台、CLI 和 Engine 文件，每个文件按打开时长度读取，防止仍在增长的日志让导出无法结束。

在线导出按以下顺序执行：

1. 后台请求 Engine 准备导出，取得刷新状态和来源覆盖；
2. 桌面归档负责人读取实际存在的受管文件；
3. ZIP 内写入日志和 `manifest.json`；
4. 接口同时返回实际包含、不可读和读取中截断的文件。

清单明确保留 Engine 报告中的“其他进程未刷新”，并注明文件在读取期间仍可能继续增长。刷新完成只说明当前后台进程的队列已经处理，不代表所有进程和所有文件完整。

后台不可用时，Tauri 的启动诊断入口仍可导出现有受管文件。离线 ZIP 的清单把模式写为离线，Engine 准备结果为空，不伪造实时刷新或零丢弃结论。

## 隐私边界

桌面只转发 Engine 已封闭的状态和计数，不复制连接失败分类、身份映射、地址或错误正文。归档清单只包含固定受管文件名、计数和状态，不包含用户内容、设备名、原始地址、路径或凭据。

Engine 的详细记录不会进入桌面 Sentry。桌面远程开关与本地详细记录相互独立。

## 验证边界

本机验证覆盖真实后台进程、认证客户端、重复开启、编号隔离、正确停止、在线 ZIP、清单内容、正常退出和重启回到标准模式。前端通过 DOM 交互测试覆盖状态加载、开关、响应丢失恢复和离线导出。

内容级验收另外使用真实本机连接和缺失认证材料，要求诊断记录能分别说明连接用途、候选来源、每次尝试、连接终态、客户端认证拒绝、服务端失败位置以及后续恢复决定。归档测试从 ZIP 回读 Engine 记录并逐字段比较，避免只验证文件名和压缩包可打开。

macOS 图形界面的实际页面点击、系统睡眠、Windows、Linux 和跨设备故障复现仍须在对应环境单独记录，不能由主机测试代替。
