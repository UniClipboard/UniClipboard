# 历史列表的有限内存窗口

历史列表与网格使用同一个记录窗口。窗口最多保留 50 条已解密记录，另外独立保留一条所选记录的投影；所选记录仍在窗口中时复用同一对象。会话快照仅保存在进程内存中，同样限制为 50 条记录与一条所选投影，并单独保存所选标识、绝对索引和滚动状态。持久化历史不受此限制。

滚动期间，窗口从可见范围上方最多 10 条开始，最多加载 50 条。停止滚动 750 毫秒后，窗口收缩到可见范围及上下各最多 10 条。历史开头和结尾按实际记录数收缩。如果可见记录多于 30 条，先保留可见记录，再按 50 条总上限分配缓冲区。

`useHistoryWindow` 按 `offset` 和 `limit` 请求当前窗口。切换时继续显示旧窗口，在请求所缺范围并与重叠记录合并完成后，一次发布完整的 `{offset, items}`，不再先发布缩小的重叠窗口。被移除的记录在反向滚动时重新读取。新请求会取消旧请求，过期响应不得覆盖新窗口。若被取消的是刷新请求，新请求必须继承刷新要求，完整读取新范围，不得复用旧记录与新偏移混合拼接。空闲收缩也遵守该刷新归属。筛选改变时从第一条重新加载。实时新增、界面删除和连接恢复会重新读取当前窗口。新增通知直接使当前窗口失效，不再另读历史头部的 50 条内容。

## 全局滚动范围

有限窗口使用原生滚动容器，其他未使用有限窗口的组件继续使用原有虚拟列表。`HistoryWindowViewport.total` 来自搜索接口的当前结果总数。三个皮肤的列表与网格均使用共享的上下占位计算：列表顶部为 `offset × rowHeight`，底部为 `max(0, total − offset − length) × rowHeight`；网格顶部行数为 `floor(offset / columns)`，底部行数为 `max(0, ceil(total / columns) − ceil((offset + length) / columns))`，首张卡片按绝对索引的列余数对齐。未加载区域不渲染日期标题。

行高优先使用已渲染行之间的实测间距中位数，无测量时使用相对单位估计。同一列数与卡片尺寸下固定实测估计，避免每次换页都把局部日期标题、残行误差放大全局；列数或卡片尺寸变化后重新测量。日期标题和实际几何的误差继续由原有的可见记录标识与相对顶部锚点，在布局阶段补偿。占位高度变化使用同一补偿入口，原生 CSS 滚动锚定保持关闭，普通重新渲染不得覆盖用户滚动。

可见范围回调仍报告相对当前窗口的索引，由数据钩子转换为绝对索引。拖动滚动条进入纯占位区时，先按 `scrollTop / rowHeight` 和列数计算绝对范围，再减去窗口偏移报告，因此可以直接跳到尚未加载的位置。快速连续输入允许取消尚未完成的窗口请求。

待接收占位行只在未筛选浏览的头部实际渲染，与真实记录合计最多 50 行。它们的逻辑位置在深层窗口中由顶部占位保留，总数与深层偏移都计入这些位置；数据层统一把可见范围和方向键目标转换回搜索接口的记录索引。所有占位高度均钳制为非负。复制后的置顶由后端排序负责，不在深层窗口里局部重排；复制成功后按当前偏移原地重新读取窗口，不滚动到顶部。被复制的所选条目若因置顶离开当前窗口，按离窗处理，继续保留所选投影，方向键从它的新位置移动。

如果整个全局范围都能放入视口，滚轮不会产生原生滚动事件。此时滚轮的垂直输入和 PageUp/PageDown 直接请求较新或较早的 10 条记录。存在原生溢出时仅使用原生滚动，避免一次输入移动两次。到达历史首尾后停止移动。

## 选择与缓存生命周期

1. 内存上限为窗口 50 条记录，加一条独立保留的所选投影。记录从窗口移除不代表从结果集删除；移出时保留选择与详情，重新加载时更新所选投影。已确认删除清除或替换选择；刷新后在已知索引覆盖范围中消失的条目按已不属于结果处理。
2. 所选条目已移出窗口时，方向键仍从其绝对索引移动。控制器请求目标邻居所在窗口，选择该邻居并在窗口替换的同一布局阶段将其带入视口，不从首个已加载条目重新开始，也不先按旧滚动位置请求另一个窗口。窗口重载时通过重叠记录的标识校正索引；离窗导航先校验所选标识的实际位置，旧索引失效时逐页查找，每页最多 50 条且不缓存探测页，定位后才原子发布邻居窗口。探测与普通请求共用取消和刷新归属，用户继续滚动时取消探测，显式邻居定位期间的被动空闲收缩等待定位完成。`aria-activedescendant` 只指向当前实际渲染的条目。
3. 新条目到达时，只有可见范围仍在顶部、窗口偏移为零且首条被选中，才跟随新的首条。深层浏览及正在查看其他条目时保留选择。
4. 查询或筛选变化后，以新结果的头部窗口证明成员关系；所选标识不在该窗口且无法低成本证明仍属于结果时，保守地清除选择与旧详情。之后延续原有的无选择时自动选择第一条规则。结果尚未返回时不拿旧窗口证明新结果的成员关系。
5. 多选只保留标识及批量置顶所需的布尔状态，不保留额外条目投影。移出窗口不取消勾选；已确认删除移除对应标识，新查询返回后只保留其头部结果能证明属于结果集的标识。批量删除、置顶和标签操作仍作用于完整勾选集合。

详情预览缓存保留窗口内标识与所选标识，所选预览及其未完成请求不因窗口淘汰而被清除。所选投影、预览和会话快照均为进程内存状态，不新增持久化内容。

图片预加载只遍历实际渲染的记录窗口。普通图片 URL 预算保持 50，所选详情另有一个固定预留槽，总计最多 51。详情描述符通过独立租约预留该槽，离开窗口不会撤销所选详情 URL；切换选择或关闭详情时释放租约。图片 URL 区分可见组件引用和缓冲引用，可见组件引用固定 URL，缓冲引用允许缓存淘汰。普通 50 槽满且全部被固定时，新普通请求按繁忙状态退避重试，不得挤占所选槽或撤销可见 URL。最后一个使用者和所选租约都离开时撤销 URL，并取消未完成请求。旧请求不得重新填充已释放的缓存。锁定状态继续由 Engine 和宿主授权控制，缩略图不可用时不读取原图兜底。繁忙条目进入下一轮重试，不得阻塞其他条目。可见请求和预加载共用带随机抖动的指数退避，延迟上限为 8 秒加抖动。

## 端到端验收

先构建真实 daemon、Go CLI 和 macOS acceptance 应用包，再运行：

```bash
python3 apps/gui-go/e2e/history_window_run.py \
  --repo . --app target/acceptance/UniClipboard\ E2E\ Test\ Build.app \
  --out .planning/history-window-list.json
python3 apps/gui-go/e2e/history_window_run.py --grid \
  --repo . --app target/acceptance/UniClipboard\ E2E\ Test\ Build.app \
  --out .planning/history-window-grid.json
```

场景使用独立 HOME、独立 profile 和 120 张合成图片。系统剪贴板保持禁用。场景检查双向滚动顺序、记录上限 50 与图片 URL 上限 51、空闲收缩、窗口外图片 URL，以及历史头部和深层分页位置的新增与删除。新增图片经过真实接收路径。常规场景先以连续短间隔滚动采样滚动条比例，要求回退不超过 1%，与首条可见记录的绝对索引比例在视口覆盖率允许的误差内一致，并验证所选记录被移出窗口后详情不变。该步骤由原生 Python 运行器与原有场景一起强制验收。删除经过界面确认流程。场景必须先确认界面总数从 120 变为 121，再变回 120。新增和删除前后的同一可见条目垂直偏移不得超过 2 像素。保留的可见记录必须保持同一个 DOM 节点，图片必须已成功解码。结果记录源码、场景和二进制哈希。Windows 需要在相应原生桌面上另行验收。


大视口场景使用真实原生 WebView，并通过窗口 API 调整大小。无全局溢出时验证 50 条全部可见并使用显式前后导航；全局占位仍造成溢出时验证原生滚动，且轮滚与 PageUp/PageDown 不得同时触发显式窗口移动。单元测试另覆盖完全无溢出的分支。脚本化滚轮事件不等于物理触控板手感验收。

```bash
python3 apps/gui-go/e2e/history_window_run.py --grid --large-viewport \
  --repo . --app target/acceptance/UniClipboard\ E2E\ Test\ Build.app \
  --out .planning/history-window-large.json
```

Linux 构建必须使用 `UC_UI_PLATFORM=linux` 和 `gtk4,e2e`。在独立 D-Bus 会话及 Xvfb 中运行同一个场景：

```bash
dbus-run-session -- xvfb-run -a -s '-screen 0 2560x1920x24' \
  python3 apps/gui-go/e2e/history_window_run.py --repo . \
  --gui target/gui-go/gui-go --grid --large-viewport \
  --out .planning/history-window-linux-large.json
```

`.github/workflows/history-window-gui-e2e.yml` 提供独立 Linux 运行器。该场景验证 WebKitGTK 的视口、导航和缓存上限，不验证 Wayland、物理输入或完整 Linux 桌面交互。


GitHub 托管 Ubuntu 运行器通过现有 `prepare-webkit-container-profile.sh` 创建专用 AppArmor 配置。只有本次验收进程通过 `aa-exec` 使用该配置，允许 WebKit 创建沙箱所需的用户命名空间。先用 bubblewrap 验证该前提，再启动 GUI；不关闭 WebKit 沙箱或主机命名空间限制。

手动触发工作流时，可用 `reuse_binaries_from_run` 指定同仓库的历史构建运行。工作流先比较全部产品输入和前端源码，再核对三个二进制的校验和。任何差异都会失败。运行器与 CI 环境允许变化；工件中的二进制仍保留原始构建提交，不改标为当前提交。
