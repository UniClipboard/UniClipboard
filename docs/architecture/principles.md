# 架构原则

产品方向、安全底线和锁定决策以 [VISION.md](../../VISION.md) 为准。本文只说明当前架构如何落实这些约束。

## 所有权与依赖

Engine 拥有跨平台核心。桌面仓库只通过固定版本的 `uc-engine` 公开契约使用核心，并提供平台能力。Engine 内部保持六边形架构：领域定义业务概念与 Port，应用层编排用例，适配器实现外部能力。不得在桌面仓库重建或直接依赖 Engine 内部包。

桌面 GUI 与用户 CLI 是 daemon 的客户端。GUI 不打开业务数据库，不内嵌 Engine。daemon 不依赖 GUI 框架。具体模块职责见 [模块边界](module-boundaries.md)。

## 单一事实来源

- 核心业务规则、加密和协议由 Engine 维护。
- daemon API 传输合同由 `uc-daemon-contract` 维护。
- 平台目录由 `uc-app-paths` 解析。
- 窗口、快捷键和桌面本机主题由 Go/Wails 宿主持有。
- 前端只持有显示和交互所需状态，不维护平行业务规则。

跨边界时，在目标合同所属模块完成数据映射。不得为方便调用而把传输类型放入领域层。不得保留无删除计划的新旧实现。

## 变更顺序

1. 明确用户动作、成功结果和失败形式。
2. 确定能力属于桌面宿主还是 Engine。
3. 复用当前公开契约和依赖。
4. 若必须改变核心能力，先在 Engine 实现并验证。
5. 更新桌面固定提交，并通过最小端到端路径验证行为。

Port 演进、跨 crate 转换与提交边界见 [架构规则](../agent/architecture-rules.md)。启动、事件消费和关闭职责见 [启动架构](bootstrap.md)。公开能力见 [uc-engine 接口](uc-engine-interface.md)。

## 安全与验证

用户内容持久化必须加密。凭据只进入系统安全存储及明确列出的受限例外。配置可以明文保存，但不得包含用户内容或凭据。完整范围以 [VISION.md](../../VISION.md) 为准。

优先使用端到端验证。验证应保留可重复的步骤和可核对的工件。构建成功、模拟回放和真实设备验收属于不同证据，不得混称。
