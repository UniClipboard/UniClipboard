# 桌面启动与资料升级进度

后台负责一次完整启动，Engine 通过 `StartupProgress` 报告公开的产品进度；桌面窗口只观察，
不解析升级恢复文件、不打开数据库，也不编排 Engine 内部步骤。

## 启动期间的访问

取得 profile 实例锁并发布 PID 后，后台先绑定仅监听 `127.0.0.1` 的启动状态服务，
再调用 `Engine::start_with_progress`。`daemon-startup.conn` 使用已有连接文件格式和原子发布方式，
保存状态服务的地址、认证令牌和进程身份，不保存用户内容或进度。

该文件与 `daemon.conn` 分开：启动服务不能被旧客户端的业务健康探测误认为不兼容服务并终止。
状态入口只有认证后的 `GET /startup`；没有业务操作、密码输入和远程访问入口。
客户端先核验 PID 身份和回环地址，再携带 Bearer 令牌请求快照。响应禁止缓存。
正常业务服务仍按原有流程初始化并发布 `daemon.conn`，不构造半初始化的 Engine。

`DaemonStartupStatus` 在 Engine 公共快照之外保留 `service_ready` 和 `service_failed`：
前者在业务监听已绑定且连接文件已发布时设置，后者表示宿主业务服务失败。
Engine Ready 本身不代表 GUI 已连接。只有后续健康校验、会话交换和 WebSocket 连接成功，
界面才进入正常应用。进度快照只存在后台内存中，重开窗口会重新请求最新状态。

## 等待、恢复和重试

界面共享一个有界最新快照和单个在途请求，按尝试标识与序号过滤同次尝试的迟到状态。
窗口订阅停止后停止轮询；业务连接成功后也不再持续查询启动状态。

前端移除了独立的 12 秒失败计时。原生等待与前端连接等待在有认证的、未结束的启动任务时继续；
无启动任务或状态服务失联时仍保留原来的等待期限。冷启动动作采用同样的活跃任务判断。
这是存活状态判断，不承诺任务有进展；不因为耗时长或计数暂时不变就重启升级。

Engine 失败后后台保留终态供界面读取，直到明确重试或退出。启动任务被中止时由 Engine
提供 Interrupted；进程被强制终止时通过 PID 与连接失败识别，不信任遗留发现文件。
真实服务启动失败同样保持可诊断的状态。

GUI 重开优先连接正在启动的后台，不再重复拉起。主动重试在原生端串行执行，拒绝打断
活跃启动，也尊重 Engine 的重试许可。成功连接后清除旧启动失败记录；晚到的业务就绪
也会更新连接，从而允许界面自动恢复。

## 界面与兼容

前端类型由 Tauri 导出命令的共享 DTO 生成，不再维护另一份手写 Engine 快照类型。
只展示当前步骤的真实处理量，未知总量保留不定进度；内容表示数量不称为历史条数。
处理记录保留有限步骤与警告；没有启动前密码输入能力，不显示不可执行的解锁按钮。

独立的开发预览仍受 `import.meta.env.DEV` 门控，与正常启动无关。
本次不改变移动绑定和 CLI 的启动等待策略，不新增 CI 配置。

## 验证入口

- `crates/uc-webserver/tests/startup_progress.rs`：认证、就绪前访问、终态与清理。
- `crates/uc-desktop/src/startup/`：统一启动协调入口，内部组织启动动作和进度等待；覆盖 147 秒等待、缺失任务超时、中断失败。
- 前端连接等待、自动重连、重试去重及界面测试。
- `.planning/research/upgrade-progress/verify-runtime.mjs`：独立 alpha.5 合成 profile 的真实后台升级和再次启动。

长时间场景使用模拟时钟；合成 profile 不等于原用户完整资料验收。Windows 真机和原用户资料
的新增完整界面流程验证必须单独记录，不能用上述测试代替。
