# 0015 · 纯 CLI、无头服务与独立桌面集成

- 状态：已采纳，待实现；本文中的进程拆分、命令与本机适配协议均为目标设计，不代表当前已经支持无头运行。
- 日期：2026-11-09。
- 关联：[0003 Engine SDK](0003-engine-sdk.md)、[0005 仓库布局](../archive/0005-monorepo-layout.md)、[0006 macOS 客户端](0006-macos-swiftui-client.md)、[0008 设备身份](../archive/0008-device-identity-and-backend-bindings.md)、[Engine 契约](../../contracts/engine-contract.md)、[历史契约](../../contracts/history-contract.md)、[提交契约](../../contracts/pipeline-contract.md)、[Action 契约](../../contracts/clipboard-action-contract.md)。

## 背景

当前 Go 桌面端把 CLI 与 mygo GUI 编入同一个 `unic`；`unicd` 虽然不创建主窗口，仍无条件运行 `mygo.App.Run()`，并通过 mygo 读写系统剪贴板、创建托盘和通知。Linux 的 mygo 初始化需要可用的图形显示环境，托盘创建失败后继续运行并不等于支持无头环境。

此外，当前 `unic copy` 先写系统剪贴板再提交，`unic paste` 读取系统剪贴板。只增加“隐藏窗口”或“无托盘”参数，不能满足服务器、容器和无桌面登录会话的使用需求。工作区已有的目录剪贴板适配用于多节点端到端测试；替换 Board 不会消除 daemon 对图形运行时的依赖，也不定义正式的无头产品语义。

无头用户需要通过 CLI/API 配对、审批、提交文本和文件、查看接收记录、读取或导出内容、调用插件 Action。桌面用户仍需要系统剪贴板自动同步和 GUI，安装过程应尽量简单。

## 决策

### 1. `unic` 是纯 CLI，`unicd` 是无图形依赖的本机服务

```text
unic CLI ───────────────────────┐
GUI（mygo / SwiftUI）───────────┼── 本机 IPC ── unicd ── Engine / 插件 / 网络 / 历史
桌面适配器（剪贴板、通知、托盘）─┘
```

| 部分 | 职责 | 运行条件 |
|---|---|---|
| `unic` | 命令行参数、stdin/stdout、本机 API 客户端 | 无需图形库或桌面会话 |
| `unicd` | Engine 生命周期、配置、插件装配、本机 API、内容与历史 | 无需图形库或桌面会话 |
| 桌面适配器 | 系统剪贴板观察/应用、防回环、权限、主线程与系统集成 | 用户的图形登录会话 |
| GUI | 查询与操作界面 | 用户的图形登录会话 |

`unic` 与 `unicd` 的生产依赖图不得包含 mygo、SwiftUI 或其他桌面工具包；不能只靠运行时分支跳过初始化。默认发布的这两个程序本身就可无头运行，不要求用户自行设置 build tag 或准备虚拟显示服务。根模块可以继续包含桌面依赖，无需为了依赖下载范围立即拆 Go 模块。

`unicd` 是每个状态目录唯一的 Engine 所有者。CLI、GUI 和适配器不直接打开 SQLite，不创建同一身份的第二个 Engine，不另建历史库。无头与桌面使用同一套设备身份、信任、后端配置、历史与提交逻辑。

### 2. 桌面集成是独立客户端，GUI 与适配器可共用进程

首版 Go 桌面程序命名为 `unic-desktop`，承载 mygo GUI 与桌面适配器；GUI 窗口关闭后，适配器可留在用户会话中继续运行。macOS SwiftUI 应用接入时可承载相同职责，以平台原生 API 实现剪贴板适配。它们都是 `unicd` 的客户端。

一个状态目录同时只允许一个活动剪贴板适配会话；Go 桌面程序与 SwiftUI 应用不能同时观察和写入同一个服务的系统剪贴板。主窗口、快速面板等可以有多个客户端，但必须经过唯一适配会话执行系统应用。

这取代 0006 中“系统剪贴板留在 unicd、Swift 侧不实现”的边界，以及只给 daemon 增加无托盘模式的安排。Swift 侧只增加系统适配，不重复实现处理流水线、历史、配对或网络。托盘与通知归桌面程序，不再归 daemon。

退出主窗口不停止同步；明确退出桌面程序后，系统剪贴板自动捕获和应用停止，`unicd` 的接收、存储和显式提交继续运行。停止 `unicd` 则所有客户端失去服务。登录启动与服务管理分别管理 daemon 和桌面程序；具体平台安装器后续落地，不由 CLI 命令隐式拉起 GUI。

### 3. 无头模式没有“虚拟系统剪贴板”

没有适配器连接是正常运行状态，不以图形初始化失败触发降级。服务不轮询系统剪贴板，也不把历史最新条目伪装成当前系统剪贴板。

无头状态下，设备配对/审批、后端同步、插件、历史、显式内容导入/提交/读取正常可用。系统剪贴板观察与应用能力为 `unavailable`；平台本身不支持的能力为 `unsupported`，权限不足仍使用 `permission_required`。适配会话上线后报告实际能力。

必须区分“系统剪贴板能否读写”与“Engine 能否导入、存储、接收和显式导出此格式”。不能因为 `Observe/Apply` 不可用或无桌面可写格式，就过滤掉无头节点本来支持的接收内容。实现前修订 Engine 能力交集、接收过滤及处理器上下文的相关契约与测试；显式导入、提交和读取不能要求存在观察 epoch。

### 4. CLI 显式区分内容提交与系统剪贴板操作

以下为目标命令；实现时同步 CLI 帮助、HTTP DTO 与文档，不保留旧行为的自动回退：

| 命令 | 语义 |
|---|---|
| `unic submit [text]`，省略 text 时读 stdin | 直接导入并经 captured 流水线提交，来源为 explicit；不读写系统剪贴板 |
| `unic submit -f <file> [more files]` | 显式提交文件；源文件引用和变化检查遵循历史契约 |
| `unic history list/show/...` | 沿用历史查询和管理；列表只含元数据，show 是显式内容读取 |
| `unic history export <id> --output <dir>` | 将内容物化到用户指定目录，不写系统剪贴板；导出覆盖、路径与多部件规则在 CLI/API 契约中补齐 |
| `unic copy [text]` / `unic copy -f ...` | 请求桌面适配器写系统剪贴板并显式提交一次，保留当前桌面意图 |
| `unic paste` | 经适配器读取当前系统剪贴板；不以最新历史代替 |
| `unic history use <id>` | 经适配器应用历史，不重新提交或同步 |
| `unic history action <id> <key>` | 执行 Action 并返回新历史标识与提交/同步结果；默认不写系统剪贴板 |
| `unic history action <id> <key> --apply` | Action 成功后再请求适配器应用结果 |

配对、审批、设备、配置、插件、状态与事件命令仍通过 daemon 工作。`unic gui` 从 CLI 移除，使用独立桌面程序或 `.app` 打开界面。

需要系统剪贴板的命令在无适配器或无相应能力时返回机器可读的 `unavailable` / `unsupported` / `permission_denied`，不把提交成功冒充剪贴板写入成功。`--apply` 在执行 Action 前检查能力；检查之后适配器仍可能断开，Action 已提交的结果必须保留并返回其标识与独立应用失败。

GUI 的“运行并复制”仍显式请求应用。Action 核心语义保持不变：生成新历史、按显式提交策略同步，系统应用是后续独立步骤。对应本机 API 需要支持独立的执行与应用结果，不能因无头环境把已经成功的 Action 改报为执行失败。

提交结果沿用 `CommitContent/GetSubmission`：历史提交和网络结果分开，`queued/sent` 不代表远端收到、应用或粘贴。CLI 将 RequestID 暴露给调用方用于结果查询/同键重试；脚本需要确定结果时使用显式 RequestID，不因超时自动换键重发。精确参数与退出码在实现前补入本机接口契约。

### 5. 接收、保留与导出遵循 Engine 的资源语义

无头接收仍经过认证、授权、策略、去重、received 处理和 commit。没有系统剪贴板应用不阻止接收成功，也不构成新的信任或转发规则；收到的内容不自动转发给其他设备。

通常以 `persist=true` 的历史查询和显式导出消费接收内容；`persist=false` 仍按既有契约只在 Received/活动租约的保留期内可用，不为了无头模式强制入历史。实现需提供显式 Received 列表与内容读取/释放入口，使未持久化接收也可消费；Received 的 TTL、容量与重启失效必须可见，不承诺可靠离线收件箱。未应用的条目按原 TTL/容量回收，不能因无适配器无限持有资源，也不能伪报 applied。

读取 stdout、导出到文件和写入系统剪贴板是不同操作。前两者取得并释放内容租约，不调用 `BeginApply/ReportApplyResult` 伪造系统应用，不新增历史或同步。读取不隐式删除接收记录；需要移除时显式 dismiss。

本机文件提交仍默认记录源文件引用，不承诺复制一份永久附件；源文件修改或删除按 `source_changed` 处理。服务器若需提交临时生成的文件后立即删除，应等待发送完成，或使用后续明确定义的自有快照导入能力；本次不隐式改变存储政策。

导出必须在指定目录内创建内容，拒绝路径穿越和符号链接越界，默认不覆盖已有文件；失败清理本次创建的半成品。导出副本归用户管理，Engine 的历史淘汰和租约释放不删除副本。

### 6. 本机适配协议是拆分的前置工作

现有面向 GUI/CLI 的 `/v1` 查询和操作接口不足以让独立进程实现完整的剪贴板观察/应用。不能仅把 `Board` 换成空实现便宣称完成。新增本机适配协议必须覆盖：

1. **会话与代次**：注册、能力更新、独占占用、心跳/有界到期和主动注销。daemon 分配适配会话代次；旧代次的观察、应用回报与迟到请求拒绝。第二个活动适配器返回 `in_use`，不静默抢占。
2. **观察与显式复制**：导入快照、建立基线、递增 epoch/sequence、报告变化；copy 的写入、回读、基线与显式提交需在适配器串行处理，防止重复提交和吞掉用户的新复制。
3. **应用**：BeginApply/BeginApplyHistory、取得必要内容/文件租约、系统写入、回读及 ReportApplyResult；沿用现有 Engine 单应用槽、冲突检查、AppliedToken 防回环和文件租约所有权。
4. **断开与恢复**：会话失效即撤销能力并使旧观察/未完成应用失效；回收该会话持有的资源。适配器重连先上报当前真实剪贴板为 baseline，不广播现有内容；不自动重放断开期间累积的历史到系统剪贴板。
5. **通知与状态恢复**：事件仅携带公开标识和修订，不带正文、地址、票据或路径；断线/溢出后查询快照。适配器只应用会话就绪后按策略到达的新接收，旧内容由用户显式选择。
6. **有界资源**：上传大小、流数量、请求期限、待处理命令与租约数量均有限额；daemon/适配器崩溃及慢消费者不能无限保留内存或文件。客户端不可用不能阻塞网络接收与历史提交。

服务重启后所有实例内句柄和会话失效；客户端重新连接，不能用旧租约或旧应用 token 续接。实际系统写入和回报无法跨进程原子提交；断开时不确定的应用结果不得推断成功，也不自动重试写入。适配器在重新建立 baseline 前释放旧读取者和旧应用持有，文件路径的物化/生命周期须在协议契约中明确。

协议仍只对本机同一用户开放，沿用受限状态目录与 socket 权限，不新增 TCP 监听或远程控制接口。Linux 首批使用现有 Unix socket；其他平台沿用仓库已验证的本机 IPC，必要时另行验证平台实现。适配会话的独占机制用于并发正确性，不宣称在有 socket 访问权限的同用户进程之间建立安全隔离。

### 7. 仓库与分发

通用 daemon/CLI 已不属于桌面平台专属代码，目标目录调整为：

```text
app/service/
  cmd/unic/                 纯 CLI
  cmd/unicd/                无头服务
  internal/                 host、api、config、paths、插件安装与配置装配
  README.md、AGENTS.md
app/desktop/
  cmd/unic-desktop/         mygo GUI + 系统适配
  internal/                桌面剪贴板、托盘、通知、UI
app/mac/                    SwiftUI 客户端及后续原生系统适配
```

Go CLI/桌面共用的本机协议 DTO 与客户端放在根 `internal/localapi/`，不能让桌面端 import `app/service/internal`。服务端处理器留在 service；系统剪贴板适配不进入 service 或 Engine。Swift 客户端依赖协议文档/Schema，不依赖 Go internal 包。这补充 0005 的布局，仍使用单一根 Go 模块和单向核心依赖；各应用有自己的 README/AGENTS。

提供两类分发：

- **无头版**：`unic` + `unicd`，不要求安装 GUI、图形库或虚拟显示服务。允许通过用户服务管理器/容器入口运行，优先以普通用户身份使用独立私有状态目录。
- **桌面版**：将 CLI、daemon 与平台桌面程序一并安装，原生 `.app` 可封装这些产物。一次安装即可使用 GUI 和 CLI；安装包内多个程序不要求用户分别下载安装。

图形会话退出后 daemon 是否仍运行取决于服务管理器配置；不承诺所有平台跨注销常驻。一个状态目录只运行一份 daemon，多节点用各自 `UNIC_HOME`；多个桌面登录会话也不得绕过适配独占。无头版和桌面版切换使用同一状态目录，不迁移身份、不重配对；安装器不得启动第二份 daemon。

### 8. 取舍

- CLI 内嵌 GUI 省一个入口，但把图形依赖带给所有命令行用户，不能作为无头版的默认产物。
- 仅关闭托盘、使用虚拟显示或目录剪贴板绕过图形环境，不解决实际桌面依赖和命令语义。
- 为无头版与桌面版各维护一套 daemon 或 Engine 装配，会增加生命周期、插件和 API 的分叉；本方案共享唯一服务实现。
- 独立适配器引入会话、IPC 和资源交接成本，但将图形会话故障与同步服务隔离，也让 SwiftUI 能使用系统原生剪贴板 API。此成本必须通过协议与断线测试承担，不能以增加进程本身作为完成标准。

项目未发布，拆分时直接更新命令、目录、API 与安装入口，不保留旧 GUI 子命令、旧桌面 daemon 或自动回退路径；协议版本号保持为 1。

## 实施顺序与验收

1. **补齐契约**：本机服务/适配会话协议、能力模型、提交/Action 与系统应用分离、Received 读取、文件租约和导出规则。同步修订 Engine、历史、提交、Action 契约及 0006；记录目标与已实现状态，不能只改状态行。
2. **拆入口与目录**：移动公共服务代码和本机协议，纯 CLI 移除 GUI，`unicd` 移除 mygo 初始化和 Board 必选条件。系统适配实现迁到 `unic-desktop`。
3. **实现无头路径**：显式提交、历史/Received 读取和导出、无适配器状态、Action 独立结果；先通过双无头节点测试。
4. **接回桌面**：mygo 适配会话、系统 copy/paste/use、自动捕获/应用与防回环；再接 SwiftUI，避免同时保留旧 daemon 内的轮询。
5. **更新分发和文档**：构建入口、CI、README/AGENTS、安装与服务管理。测试目录 Board 保留为测试设施，与生产无头路径分别验证。

交付必须满足：

- 在未安装图形运行库、未设置 DISPLAY/WAYLAND_DISPLAY 的 Linux 环境中构建并运行 `unic`、`unicd`；依赖检查确认两者没有桌面工具包。容器测试不能偷偷挂载宿主显示或使用 Xvfb。
- 两个独立状态目录的无头节点完成配对、人工指纹核对/审批、文本/图片/文件提交与接收、历史及 Received 内容读取、导出、Action、重启后历史读取。无头支持不放宽信任和后端策略。
- 无后端、无目标、全局同步关闭、提交超时重试、persist=false、文件变化/删除均符合既有契约；没有系统应用也可提交、接收和读取。
- 无适配器时 copy/paste/use/显式 apply 给出准确错误；Action 提交成功后应用失败仍能查询结果；状态和事件不含正文/票据/地址/路径。
- 桌面启动 baseline、显式 copy 只提交一次、自动收发防回环、用户复制竞争、文件租约、适配器崩溃/心跳超时/重连、第二适配器争用、daemon 重启和旧 token 回报均通过测试；重连不自动广播旧剪贴板或应用积压历史。
- GUI 关闭与桌面程序退出的行为符合第 2 节，daemon 可独立运行；桌面和无头安装使用同一身份与目录锁。
- 通过相关包测试、`go test -race ./...`、新入口构建及各桌面平台实际剪贴板验收；Linux 无头验收不能代替 macOS/Windows 图形会话验证。

本次仅确定设计并登记文档，不修改运行代码、发布安装包或宣告以上验收已通过。
