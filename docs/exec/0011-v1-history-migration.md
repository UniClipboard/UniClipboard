# 0011 计划讨论稿：从 UniClipboard v1 迁移本机历史与标签

- 日期：2026-11-08。
- 状态：源码调研完成，产品行为与接口边界待讨论；尚未实施。
- 来源仓库：相邻的 `../../../engine` Rust workspace，当前 workspace 版本为 `1.1.0-rc.23`。本文“v1”指旧产品，不能与其内部 V1/V2/V3 存储格式混为一谈。
- 目标仓库：当前 unic Go 核心与桌面宿主。
- 依据：[Engine 契约](../design/engine-contract.md)、[历史契约](../design/history-contract.md)、[0003](../design/decisions/0003-engine-sdk.md)、[0005](../design/decisions/0005-monorepo-layout.md)。

## 1. 用户目标

用户选择本机 v1 数据目录，授权读取旧 Keychain；读取失败时允许输入旧口令。工具解密历史正文、标签及所需 blob，导入当前版本的数据目录。完成后打开当前版本，即可浏览和使用迁移的历史。

明确迁移范围是历史记录、tag 定义及关联、历史依赖的内容。设备身份、配对关系、网络凭据和设置不在本次需求内。读取密钥仅服务于解密，不将旧设备身份作为新版本身份导入。

“全部历史”需要在讨论中明确：建议指选定 profile 中仍保留、尚未删除的历史，保留同内容的多条记录。原库已删除或原文件已丢失的字节不能通过迁移重建。

## 2. 已确认的源码事实

### 2.1 旧目录与解密

旧版早期布局使用 `uniclipboard.db`、`vault/`、`file-cache/`，但当前 Rust engine 还支持 V3 profile 布局。V3 通过活动 manifest 与独立 generation 定位 `profile.sqlite` 和 `blobs/`，不能只检查根目录数据库。

旧系统安全存储的 KEK 逻辑键为 `kek:v1:profile:{profile_id}`。`vault/keyslot.json` 保存 salt、Argon2id 参数与被包装的 MasterKey。口令经 Argon2id 派生 KEK，再以 XChaCha20-Poly1305 解包 MasterKey。

V3 还使用 `profile-content-key-vault-v1.json` 保存内容密钥目录，并使用 `profile_content_vault_key:v1` 对应的密钥打开它。当前实现可通过 KEK 保护的 `vault/profile-secrets-v1` 恢复独立秘密。输入口令能否解开全部历史取决于源格式和实际保留的材料，不能将所有错误都归为口令错误。

Keychain 的实际 service/account、应用签名和授权行为由旧宿主的 `HostSecureStorage` 适配决定；Rust engine 只定义逻辑存取接口。仅凭本次 engine 源码不能确定可交付 CLI 的 Keychain 访问行为，需要补查实际发布宿主。

旧 blob 包含 UCBL framing、认证加密和 zstd 压缩，源码存在内部 V1/V2/V3 分支。V3 正文还依赖带 key id/epoch 的内容保护。不能只复制密文文件，也不能把一个 MasterKey 当作所有记录唯一的解密材料。

主要源码：

- `uc-core/src/app_dirs.rs`。
- `uc-infra-profile/src/security/profile_runtime_layout.rs`。
- `uc-infra-security/src/key_material.rs`。
- `uc-infra-profile/src/security/profile_key_recovery.rs`。
- `uc-infra-security/src/profile_content_key_vault/`。
- `uc-infra-content/src/encrypted_blob_store.rs`、`content_protection/blob_store.rs`。

以上路径均相对于旧仓库 `crates/`。

### 2.2 历史并非一条正文加一个 blob

旧模型包含 entry、event、多个 representation、selection、blob 和文件集合；文件集合还包含目录结构。现有 Engine `ExportEntry` 选择一份资源导出，不代表完整导出该历史的所有格式、文件和元数据。

旧历史列表按 `active_time_ms` 降序，另有创建、捕获时间及收藏等字段。当前 Go 历史按提交序号降序。迁移需要同时决定时间字段映射与插入顺序，直接按旧列表顺序追加会使显示顺序反转。

旧版可有未落齐或已不可恢复的 payload、失效的文件引用。预检应区分原数据缺失、解密失败、目标不支持和导入失败。

### 2.3 tag 模型有差异

| 项目 | 旧版 | 当前版本 |
|---|---|---|
| 身份 | 独立、不透明 tag id | 条目上的字符串 |
| 名称 | NFC、去首尾空白，按 Unicode 小写判断同名 | 非空 UTF-8 字符串，按字节去重 |
| 名称上限 | 64 个 Unicode 标量 | 64 个 UTF-8 字节 |
| 数量 | profile 最多 1000 个标签 | 每条最多 32 个 |
| 无关联标签 | 独立 tag 定义可以存在 | 没有对应实体 |
| 持久化 | 名称、创建时间与关联均加密 | `clip_tags` 保存名称与条目关联 |

不能通过截断中文 tag 或静默丢弃无关联 tag 宣称迁移完整。是否扩展当前标签模型，必须先讨论。

旧实现来源：`uc-core/src/clipboard/history_tag.rs`、`uc-infra-storage/src/db/repositories/history_tag_repo.rs`。

### 2.4 目标导入路径尚需补齐

当前 Go Engine 的 `ImportContent` 创建内容租约，普通 commit 再创建历史，创建时间取当前时间。不存在现成的、可指定旧时间且具备持久导入幂等性的迁移入口。

当前只接受 `text/plain`、`text/html`、`image/png` 和文件；旧 representation 不能假定全部可表达。目录结构、其他 MIME、空正文和超过现有限额的历史需要预检及产品决策。

当前默认历史上限 10000 条、4 GiB，总自有内容默认 8 GiB，普通导入/提交可能淘汰已有历史。只在迁移进程临时放宽限制，不能保证应用后续普通提交时仍保留全部记录。

当前目标正文和 tag 的保存路径未采用旧版的内容加密方案。是否接受按当前存储方式导入，需要作为迁移界面的已知行为讨论；本计划尚未决定为目标增加静态加密。

## 3. 建议架构，待确认

建议采用“Rust CLI 负责完整读取和解密，Go Engine 负责目标入库”的双边边界。

```text
桌面迁移会话
  ├─ 启动独立 Rust CLI
  │    └─ 只读旧 profile、解析布局、请求解锁、完整导出
  └─ 调用 Go Engine 的专用历史导入能力
       └─ 校验、持久化内容、保存元数据与 tag、登记幂等映射
```

CLI 基于旧 Rust engine 仓库构建，复用其解密与格式读取能力；缺失的完整导出能力应在旧仓库按原有分层补齐。当前公开 Engine 接口不足以直接组成完整迁移。

建议不让 Rust CLI 直接写当前版本 SQLite：目标历史、blob 生命周期和配额属于 Go Engine；否则 Rust 也必须维护当前数据库布局、清理规则和资源账本。

如果坚持“一个 CLI 独立完成源读取和目标写入”，需要另行确定编排方式，例如由 Go 迁移程序调用 Rust reader；这与“Rust reader 单独导出”是不同交付形态，尚未选定。

桌面会话负责进度、取消、口令输入与最终报告。调用链中应有一个迁移负责人，统一拥有重试、取消、恢复和成功判定。

### 3.1 只读源数据

- 建议首版要求退出旧程序，固定迁移源，避免数据库快照与 blob 回收之间发生竞争。
- 只读打开旧数据库；若需要副本，使用一致 SQLite 快照，处理 WAL，不能只复制主数据库。
- 不直接启动完整旧 Engine：启动恢复、升级、后台清理和网络行为可能修改源数据。
- Keychain 只读；输入口令的 fallback 不写回旧 Keychain，不删除旧凭据。
- 不直接复用带 `persist_authenticated_kek`、`activate_or_migrate` 等副作用的恢复工作流；增加迁移专用只读解锁能力。
- 源库、源 blob、旧 vault 与源缓存均不移动、不删除、不升级。

### 3.2 进程间内容传递

建议使用私有继承管道或本地受限通道，采用有界二进制内容帧和结构化控制消息。大 blob 不放进单个 JSON/base64 消息。

至少需要源检测、需要口令、就绪、记录元数据、内容分块、进度、取消和终态报告。口令经私有输入通道传递，不放 argv、环境变量或日志。

默认不生成完整明文中间归档。若实现需要明文暂存，必须定义私有权限、容量、失败与崩溃后的清理；目标已提交内容的保留策略与暂存清理分开。

旧 reader 当前部分 API 会整块读取/解密 blob；协议分块不代表 reader 内部已达到流式内存边界。实施前须确定单 blob 上限、并发度及大图转换预算，并测量峰值。

## 4. 导入语义建议，待讨论

1. 预检先给出源格式、记录数、tag 数、所需容量、不可恢复项及目标不支持项；授权解锁后才能完成依赖解密的统计。
2. 全新目录与已有历史目录都应先判定支持方式，不以覆盖数据库来混合两者。
3. 不走 captured/received 普通处理链；迁移不自动改写正文、应用系统剪贴板或派发网络同步。
4. 新 HistoryID 与旧 entry id 建立持久映射。幂等键绑定稳定源标识、profile 与旧 entry id；不能只按正文 hash 去重，同内容的不同记录必须保留。
5. 将正文、tag 关联和幂等映射作为同一记录的提交单位；blob 先准备再发布数据库引用。崩溃重试不能产生重复记录或已发布的缺失 blob。
6. 保存旧时间；决定按捕获时间还是旧列表活动时间恢复顺序，按选定顺序从旧到新写入。相同时间需要稳定次序。
7. 迁移来源建议显式表达，但具体 Origin 枚举与源元数据尚未确定；不伪造已配对设备或已同步成功状态。
8. 自有 blob 导入后归当前 Engine 管理，不能让它依赖随时可删除的旧数据目录。原本仅为用户文件引用的记录，需另定复制或保留引用策略。
9. 迁移前核算既有历史与全部导入量，容量不足先阻止写入；迁移不得通过自动淘汰来“完成”。正常运行时的后续配额策略也需落地。
10. 完成后关闭并重新打开目标 Engine，通过公开历史/内容接口验收，再通知 UI 刷新。

“成功”至少分成完整完成、存在待处理项、取消、失败。存在缺失内容、未导入 tag 或不支持格式时，不能显示“全部迁移完成”。

可以选择逐条提交并断点续跑，也可以选择全部成功后统一可见；这是待确认的产品行为，当前不预设整库原子事务。

- [ ] 确认全部历史、文件/目录、其他格式、空 tag、收藏、时间与排序的语义。
- [ ] 确认目标已有历史时的追加方式、幂等策略、容量与失败可见性。
- [ ] 形成正式设计决策和源导出/目标导入契约，再开始代码实施。

### P1：Rust 只读迁移 reader 与 CLI

- [ ] 检测旧布局，固定依赖版本和支持矩阵；未知格式明确拒绝。
- [ ] Keychain 解锁及不持久化口令 fallback。
- [ ] 完整遍历 entry、representation、文件集合、tag 定义与关联。
- [ ] 内容认证解密、解压和完整性校验；分离损坏、缺失和未支持情况。
- [ ] 专用 CLI 控制协议、取消、进度和不含正文的报告。
- [ ] 证明源目录与 Keychain 未被修改。

### P2：Go Engine 专用历史导入

- [ ] 增加旧时间、稳定映射及来源表达，维护公共契约。
- [ ] 解决标签及内容表达差距；不能以静默截断代替。
- [ ] 定义迁移提交边界、持久幂等和重启清理。
- [ ] 不触发处理、同步和剪贴板写入；不淘汰已有记录。
- [ ] 落地容量和后续运行配额策略。

### P3：应用集成与交付

- [ ] 旧目录选择/检测、授权与口令输入、预检、进度、取消和续跑。
- [ ] 打包、签名和校验 CLI，不依赖用户安装 Rust 工具链。
- [ ] 当前数据目录锁与运行中 daemon 的所有权协调。
- [ ] 重开目标验证、刷新历史与标签、展示可操作的失败报告。

## 6. 验收场景

- Keychain 可读、拒绝授权、无条目、损坏密钥；口令正确、错误与取消。
- 支持的旧存储格式、WAL 数据、profile 不匹配和未知格式。
- 文本、HTML+纯文本、PNG、其他旧格式、文件、多文件、目录、自有 blob、失效用户文件引用。
- 多字节 tag、超过当前字节/数量限制、无关联 tag、同内容多记录和相同时间。
- 超过 10000 条、超过 4 GiB、单条超限、目标已有历史和磁盘不足。
- 在 blob 暂存、单条提交、进度响应和完成前后中断；重复执行与重启续跑不重不漏。
- 迁移期间无自动同步、无剪贴板改写；源目录及 Keychain 保持原状。
- 删除测试用旧目录后，目标的自有内容仍可通过公开接口读取和使用。
- 重启应用后核对记录数、每条内容字节或校验摘要、tag 定义与关联，以及约定的时间/顺序。

当前仅进行了源码调查与文档检查，未访问用户 Keychain、未解密个人历史、未运行迁移，以上验收均未执行。

## 7. 下一轮讨论

1. 首版是否只面向 macOS？实际要支持哪些 v1 发布版本和宿主？
2. 必须完整保留哪些格式与文件行为，尤其目录、丢失文件、非 PNG 图片及其他 representation？
3. tag 是否包含无关联定义、名称和原身份？是否愿意扩展当前版本的标签模型来完整承接？
4. 时间与排序按最初捕获还是旧版最近使用？收藏、置顶是否纳入？
5. 是否允许向已有数据目录追加？中断前已导入内容立即可见，还是全部完成再可见？
6. 存在坏记录时是停止、保留占位条目，还是允许明确标为部分完成？容量超默认上限后如何持续保留？
7. 是否接受“Rust CLI 解密导出 + Go Engine 入库”的分工，以及按当前版本的存储方式保存迁移内容？
