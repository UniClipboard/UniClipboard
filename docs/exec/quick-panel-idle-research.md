# Quick Panel idle footprint and activation latency

Windowless standby is implemented. The numerical thresholds below are proposed and require native measurements. The research baseline was `2116b1ec2a080191374a57a92d8671af5af23984` with mygo `v0.9.2`. The evidence below describes that baseline.

## Evidence

- The tray owns the shortcut and captures the external target. Its warm path checks visibility, probes the role and sends activation. Cold endpoint discovery polls every 50 ms. The activate reply acknowledges a queued UI call. The first open creates the history binding, window and preview flyout. See [tray activation](../../app/desktop/cmd/unic-desktop/roles.go), [role readiness](../../app/desktop/cmd/unic-desktop/roles_native.go), and [window lifecycle](../../app/desktop/internal/desktopui/process_panel.go).
- Dismissal hides both windows. The shared history binding retains its event subscription, worker and model. Service events and retry or recovery deadlines can still request a wake. The current Windows D3D11 backend sweeps its image textures by rendered-frame age. A hidden window does not keep rendering to age out the cache. mygo already exposes hidden window creation and destruction, including destruction of child flyouts. See [live binding](../../app/desktop/internal/desktopui/live.go), [wake scheduling](../../app/desktop/internal/desktopui/live_wake.go), and [window composition](../../app/desktop/internal/desktopui/quick_panel_window.go).
- The earlier Windows ARM64 control measured about 67.5 MB of private commit with empty history and 122 MB while hidden in the image scenario. The texture-release probe removed orphaned textures without a measured decrease in process counters. The old run used a different mygo revision. Its readiness clock started at private activation and did not measure the native shortcut to the first composited frame. See [memory baseline](quick-panel-memory.md#results-and-delivery-boundary) and [resource attribution](quick-panel-root-cause.md#findings).
- PowerToys Run starts its launcher when enabled and can signal it through an OS event on the hotkey path. Apple recommends stopping hidden-window work and refreshing on return. These patterns support keeping an activation path ready and limiting work to the visible session. [PowerToys Run source](https://github.com/microsoft/PowerToys/blob/main/src/modules/launcher/Microsoft.Launcher/dllmain.cpp) · [Apple energy guide](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/WorkWhenVisible.html)

## Proposed lifecycle

| State | Ownership and work |
|---|---|
| Standby | In normal Desktop mode, start one windowless panel role asynchronously after the tray and service are ready. Keep the authenticated IPC endpoint, native event loop and existing settings observation. Keep no UI history binding, renderers, history subscription or preview payloads. |
| Opening | The tray captures the original target before activation and grants native focus as it does today. The panel creates the main window and starts a one-shot first-page text and metadata read in parallel. Use the existing history query and BoardUI composition. Render the search input as soon as it can take keys. Apply only results for the active opening and query. |
| Visible | Use the existing search, preview, action and paste paths. Create the preview flyout only on demand. Keep selected original reads, thumbnail decoding, catalogues and counts out of the first-frame dependency chain. |
| Dismissed | After the paste controller finishes any target checks and guarded reopen, cancel the view scope, close the event stream, stop its timers and destroy both windows. Keep the role ready for the next activation. Preserve the existing search, filter and selection behavior with bounded identifiers and query state if needed. Retain no history or preview payloads. |

Keep prewarming under the existing tray lifecycle admission. Lightweight mode, migration, explicit quit and update relaunch must still retire the role. An activation during prewarm joins the same role startup and carries its own captured target. An activate arriving after dismissal creates a fresh view generation. A delayed read cannot populate that view. Explicit dismissal, external blur and the 150 ms keep-open guard retain their distinct focus behavior. A failed or unavailable service must produce a responsive panel with bounded loading or error feedback. Never enable paste for an operation that has not passed its existing checks. See the [Desktop quick-panel contract](../contracts/desktop-quick-panel-contract.md).

Start with a windowless role and the existing mygo APIs. This adds standby memory before a user has opened the panel. Measure that cost and compare it with the post-use footprint. If creating the main window breaches the latency budget, measure a single hidden main window with the history binding disconnected. Keep the preview flyout out of standby. If even the windowless role breaches the memory budget, attribute the floor before changing the process boundary. Measure a cold launch on each supported target before considering an idle exit policy. Crash recovery and the interval before prewarm readiness still use the cold path.

Measure the current IPC and startup stages first. If the warm status and probe requests contribute material delay, combine the existing checks on the warm route while preserving command serialization, peer validation, toggle behavior and focus permission. If cold discovery contributes material delay, improve readiness notification through the existing launcher boundary. A shorter polling interval alone cannot resolve window creation or composition time.

## Proposed acceptance

| Measure | Proposed gate |
|---|---|
| Hotkey to usable first frame | P95 at most 200 ms after the tray reports the panel role ready. Start at the final key-down of the configured shortcut. Stop when the compositor shows the real panel and its search field owns keyboard focus and can accept input. Report P50, P95, P99, maximum and every timeout. |
| Hotkey to usable history | Record the first composited, selectable history row separately. Use a nonempty fixture and verify a history change made during standby. Also record the empty state and the service-unavailable response with their own outcomes. |
| Standby memory | Start with an incremental budget of 30 MiB for Desktop as a group over matched tray-and-service idle. Record before first use and after text, image and original-preview use. Use private commit on Windows, physical footprint on macOS and private memory from `smaps_rollup` on Linux. Report metrics per role and record GPU resources separately. |
| Standby activity | After teardown, average panel CPU at most 0.1% of one logical core over five minutes. Verify zero panel-driven render frames, history RPCs and periodic history wakeups in standby, including while the service receives new clipboard entries. |

Use a synthetic profile and paired production builds with the same flags. Establish the baseline on the current mygo pin. Run the actual registered hotkey against an external target. Sample separately after five minutes idle, during startup, and after crash recovery. Keep the cold outcomes visible even where the standby SLO does not apply. Measure macOS, native Windows ARM64 and x64, and X11 and Wayland separately. Label emulated and virtualized runs. Treat portal approval as a setup condition. Keep failed focus or input delivery in the recorded results.

Use a compositor capture for the latency pass and a capture-free run for the memory pass. Record the input event and compositor frame on a shared monotonic clock, and use an immediate input probe to verify focus. Report frame sampling uncertainty. Record input dispatch, tray callback, IPC, role readiness, main-thread entry, window construction, first composition and history results. A window visibility flag or a renderer callback is useful for diagnosis. Use compositor evidence for the latency gate. [Windows Desktop Duplication frame timestamps](https://learn.microsoft.com/windows/win32/api/dxgi1_2/ns-dxgi1_2-dxgi_outdupl_frame_info)

Reuse [Desktop E2E](../contracts/desktop-e2e-contract.md) and the [resource measurement runner](../../tools/research/quick-panel-memory/README.md). Run the process and panel contract scenarios for lifecycle, target restoration and stale completion regression. For timing, collect at least 100 warm activations per reported configuration, with separate cold samples. Preserve the first failure and set a retry limit before running. Publish the source and binary hashes, commands, raw timing and resource samples, frame evidence, summary, cleanup verdict and checksums. Check rapid toggles, favorites, service restart, configuration changes while hidden, pending paste, and repeated image preview and dismissal. These cases require native execution before accepting the thresholds.
