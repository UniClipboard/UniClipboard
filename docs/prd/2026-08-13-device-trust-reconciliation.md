# 个人设备信任核对 PRD

## 文档状态

- 状态：已确认，桌面端实施中
- 日期：2026-08-13
- 范围：桌面端优先，产品规则适用于所有完整 P2P 客户端
- Engine 状态：非恢复范围已交付；桌面端按本文件接入

## 一句话定义

当用户自己的设备对“哪些设备仍属于当前空间”产生不同认知时，UniClipboard 帮助用户看懂变化、作出本机决定，并让每个形成的空间继续明确且可控地使用。

## 背景

UniClipboard 面向同一个人的多台设备。设备可能长时间休眠、离线、丢失，或在不同时间完成软件升级。用户仍希望在线设备正常同步，也希望丢失设备能被及时移除。

这两项目标会产生真实冲突：一台设备离线期间，另一台设备可能移除了某个成员；离线设备重新上线后，不能让网络消息直接覆盖它原本信任的设备，也不能让它的旧认知撤销其他设备已经作出的安全决定。

这不是普通连接故障。用户需要回答的是：“我是否认可这次设备信任变化？”产品必须围绕这个问题设计，而不是向用户展示内部同步阶段。

## 目标用户

主要用户是同时拥有两台或更多个人设备的人，例如一台电脑、一台手机和一台备用电脑。用户理解自己的设备名称和使用情况，但不应被要求理解成员历史、分支、摘要、签名或节点协议。

典型情况包括：

- 用户主动移除已经丢失、出售或不再使用的设备。
- 某台长期离线设备重新上线，发现其他设备已经发生成员变化。
- 两台设备在彼此离线时分别修改了设备组。
- 部分设备尚未升级，暂时无法继续安全同步。
- 本机收到包含自己的移除变化，需要决定退出原空间还是保留当前空间。

## 用户任务

用户真正需要完成的任务是：

1. 确认发生了什么设备变化。
2. 判断这项变化是否符合自己的意图。
3. 清楚知道选择之后哪些设备还能互相同步。
4. 在设备形成不同空间后，清楚知道本机仍能与哪些设备同步。

## 产品原则

### 平时安静

普通设备上线、离线、资料补齐和安全的新增设备传播都自动处理。没有用户行动时，不显示警告，不要求确认。

### 破坏性变化必须明确确认

其他设备提出的移除不能由本机自动接受。用户必须知道变化来源、移除目标和选择后果，才能作出决定。

### 用用户认识的设备解释

界面使用设备名称和清楚的动作，例如“从这个空间移除 MacBook Air”。不得把“接受事件”“拒绝分支”“收敛失败”等内部概念作为主要文案。

### 不把安全问题伪装成离线

以下状态必须分开表达：

- 当前是否在线。
- 当前是否仍属于本机认可的空间。
- 双方是否认可同一个空间中的设备。
- 双方版本是否能够继续安全同步。

一台设备可以在线，但因为双方对设备组认知不同而停止同步。此时显示“离线”或“连接失败”都是错误的。

### 每个警告都要有下一步

需要用户行动的提示必须提供可执行动作或明确说明应在哪台设备上处理。没有恢复能力时，不提供无效的“重试”。

## 用户可见状态

产品只使用下面这些用户语言。内部可以有更细状态，但不能直接泄露到界面。

| 用户状态 | 用户含义 | 是否需要行动 |
| --- | --- | --- |
| 在线 | 当前可以正常同步。 | 否 |
| 离线 | 当前不可达，恢复上线后会自动连接。 | 否 |
| 正在更新空间 | 正在安全地应用已经确认的设备变化。 | 否 |
| 需要确认设备变化 | 其他设备提出了本机尚未确认的移除。 | 是 |
| 需要更新 | 对方版本过旧，升级前双方暂停同步。 | 是，在对应设备上更新 |
| 不同空间 | 双方已经选择保留不同的空间，彼此不再同步。 | 否，可手动移除对方 |
| 无法验证设备资料 | 收到的设备资料无法被安全确认。 | 是，当前没有可执行恢复动作 |
| 已退出原空间 | 本机不再与原空间同步，可以继续独立使用。 | 否，可按需添加设备 |

在线与上述设备关系状态可以同时存在。设备列表应优先展示阻止同步且需要行动的状态，并在详情中保留真实在线情况。

## 核心流程

### 流程一：本机主动移除设备

用户从设备详情点击“移除设备”。确认窗口必须说明：

- 将移除哪台设备。
- 本机将立即停止与该设备分享新的剪贴板内容。
- 被移除设备以后需要重新邀请才能加入。
- 其他离线设备可能在上线后询问用户是否认可这项变化。

用户确认后，设备页显示“正在更新空间”，但不能用“所有设备已完成”描述一次本机提交成功。

完成结果：

- 本机已经停止信任目标设备时，操作可以结束等待态。
- 其他设备尚未处理不阻止用户继续使用本机。
- 后续状态由后台自动更新，用户不需要保持窗口打开。

### 流程二：收到其他设备提出的移除

当本机第一次收到一项尚未确认的移除时：

- 立即唤起并置前主窗口，显示覆盖主窗口的不可关闭全局弹窗。
- 当前运行期间为同一项变化发送一次系统通知；应用重启后仍未处理可以再次通知。
- 点击通知聚焦同一个全局弹窗。
- 用户必须作出选择后才能继续操作主窗口；可以关闭整个应用，但不能跳过弹窗继续使用主窗口。
- 快捷面板保持可用，并显示不阻挡操作的待确认提示；它不提供决定按钮。
- 相关设备之间的同步已暂停时，要明确说明，不得继续显示为“正常同步”。

确认区域必须回答四个问题：

1. 哪台设备提出了变化。
2. 哪些设备将被移除。
3. 本机最后一次确认的空间是什么。
4. 两个选择分别会影响哪些设备之间的同步。

主要动作使用结果导向文案：

- “也从此设备移除目标设备”
- “保留目标设备，与发起设备分成不同空间”

不得只显示“接受”和“拒绝”。

弹窗不能通过关闭按钮、点击外部或返回键跳过。多项变化每次只展示 Engine 指定的当前一项，处理后重新读取完整结果并继续下一项，直到没有待处理变化。

### 流程三：应用其他设备提出的变化

用户选择“应用这项设备变化”后：

- 本机采用收到的同一项设备变化。
- 目标设备不再与本机同步新的内容。
- 如果目标包含本机，按钮文案改为“退出这个空间”，并进行第二次明确确认。退出后本机可以长期独立使用，不要求立即创建或加入其他空间。
- 完成后刷新设备列表和每台设备的同步关系。

成功提示应描述结果，例如“空间已更新”，不能声称所有离线设备已经同步完成。

### 流程四：保留本机当前空间

用户选择“保留目标设备，与发起设备分成不同空间”前，产品必须明确说明：

- 本机不会移除目标设备。
- 已经应用另一项变化的设备不会因此撤销其决定。
- 双方将处于不同空间，并停止彼此分享新的剪贴板内容。
- 本机与作出相同选择、仍属于本空间的设备可以继续同步。
- 目标设备自己的最终关系取决于它在自己的设备上作出的选择；产品不得替它推断。

这是高影响选择，需要二次确认。完成后，发起设备仍留在设备列表中，并以红色“不同空间”作为主要状态；在线状态作为次要事实同时显示。不同空间是正式支持的正常结果，不显示待办数量、不持续警告，也不要求恢复。用户以后可以手动从当前空间移除该设备。

### 流程五：不同空间长期使用

不同空间可以无限期各自使用。产品不提供合并、恢复或自动选择某一空间的入口，也不自动改动空间名称。用户需要改变当前空间成员时，使用普通的添加设备或移除设备流程。

### 流程六：设备版本过旧

只有后台明确确认对方版本过旧时，才显示“需要更新”。连接失败、离线、超时或资料错误不能推断成版本问题。

对应设备条目和详情页应说明：

- 哪台设备需要更新。
- 更新前双方暂停同步，但设备没有被移除。
- 用户应在那台设备上更新 UniClipboard。
- 更新后会自动重新检查，不需要重新配对。

本机存在可安装更新时，可以同时提供本机更新入口；不能远程更新另一台设备，也不能暗示已经替用户完成。

### 流程七：本机退出原空间

本机确认应用包含自己的移除后：

- 停止与原空间同步，不再把原空间显示为正常同步。
- 关闭强制弹窗并恢复正常主窗口；不要求用户创建或加入其他空间。
- 本地剪贴板采集、历史搜索、复制和粘贴继续可用，旧历史不自动发送到以后加入的空间。
- 设备页显示“当前未连接其他设备”，并保留普通“添加设备”入口。
- 用户以后可以继续独立使用、邀请新设备，或通过新邀请加入其他空间；旧资格不会恢复。

### 流程八：设备资料无法验证

后台明确判定资料无法验证时：

- 相关设备停止同步。
- 产品显示“无法验证设备资料”，而不是“网络错误”。
- 不展示签名、摘要或内部错误原文。
- 当前版本没有可执行恢复动作时，只准确说明限制，不提供无效重试，也不锁住主窗口。

## 页面与通知

### 设备页

设备页是设备关系结果的固定入口：

- 待处理变化由全局弹窗强制处理，不在设备页另建第二份任务队列。
- 设备页按设备显示在线、成员资格、是否处于同一空间和版本兼容情况。
- 不同空间的设备保留在列表中并标红，用户可手动移除。
- 设备列表继续展示单台设备状态；同一事实不在多个位置产生相互矛盾的文案。

### 系统通知

以下情况在当前应用运行期间发送一次系统通知：

- 新的设备变化需要本机决定。
- 首次确认某台设备需要更新，且这导致双方暂停同步。
- 首次发现没有可处理决定的不同空间或资料无法验证状态。

本机刚刚确认退出、用户主动形成不同空间时不再额外通知。普通离线、自动补齐和后台重试不发送通知。通知不提供直接决定按钮，不要求额外申请通知权限。

主窗口存在或仅隐藏时，待处理变化必须立即置前。轻量模式下界面进程已经退出，后台只暂停相关同步；不新增后台启动界面的系统通道，用户下次打开应用时再立即显示全局弹窗并发送通知。

### 决定顺序

如果后台保存了多项变化，产品每次只展示当前可以安全决定的一项。用户处理后，再展示下一项。产品不得自行排序、合并或跳过变化。

## 中断与恢复

- 用户可以关闭整个应用；应用下次打开时，未处理变化再次立即显示。
- 同一项决定重复提交不得产生重复结果。
- 提交时状态已经变化，产品应重新读取当前任务并解释“设备状态已更新”，不得继续应用过期选择。
- 网络中断不丢失用户已经完成的决定；网络恢复后由后台继续处理。
- 产品收到状态变化提醒后重新读取完整当前结果，不拼接零散过程消息。
- 提交失败时保留全局弹窗，显示重试动作；只自动重新读取状态，不自动重复提交用户决定。
- 状态已经变化时，原地展示最新待处理变化；若已无待处理变化，关闭弹窗并提示“设备状态已更新”。
- 普通弹窗和未保存设置在强制弹窗后恢复，且不自动保存；过期的主动移除确认直接关闭，用户需要时重新发起。

## 隐私与安全

- 用户界面只展示完成决定所需的设备名称、设备标识、变化内容、影响范围和稳定状态。
- 不展示或记录成员实例、签名、历史摘要、密钥、网络地址、文件名、路径或剪贴板内容。
- 设备名称、决定详情和影响关系如果需要持久化，必须加密保存。
- 系统通知不得包含完整设备标识或其他可用于关联真实身份的信息；优先使用用户已经设置的设备名称。
- 分析事件只记录稳定的产品结果类别，不记录设备身份或设备关系图。

## 非目标

- 不建立账号、管理员、固定主设备或服务器审批。
- 不要求所有设备同时在线才能移除设备。
- 不自动选择某个设备组为正确结果。
- 不合并不同设备组的剪贴板历史，也不补发分歧期间的内容。
- 不允许产品端根据在线状态、设备数量、到达顺序或版本号推断应接受哪项变化。
- 不在本 PRD 中规定 Engine 的内部数据结构、协议消息或保存方式。
- 不在本 PRD 中完成最终视觉稿和逐像素布局。

## Engine 产品能力需求

本节描述产品为了完成上述用户任务必须获得的事实和动作，不规定 Engine 如何实现。

### 用户问题与能力对应

| 用户需要回答的问题 | 产品必须获得的能力 |
| --- | --- |
| 发生了什么？ | 返回当前待处理变化及其稳定编号。 |
| 谁提出了变化？ | 返回经过确认的来源设备。 |
| 哪些设备会受影响？ | 返回移除目标和两个选择各自的影响范围。 |
| 我现在还能和谁同步？ | 分开返回在线情况、成员资格、设备组一致性和版本兼容情况。 |
| 我的选择是否已经生效？ | 返回明确的决定结果和决定后的完整当前状态。 |
| 关闭应用后还要重新处理吗？ | 持久保留待处理变化、用户决定和当前设备关系。 |
| 分成不同空间后怎样使用？ | 返回每台设备的空间关系；每个空间独立继续使用。 |

### 完整当前结果

Engine 必须一次返回当前 Space 的完整产品状态，使产品可以在丢失通知、重启或晚打开页面后恢复真实界面。产品不能依赖本地拼接历史消息。

完整结果至少需要表达：

- 当前是否存在需要用户决定的设备变化。
- 当前可决定变化的稳定编号。
- 提出变化的设备。
- 将被移除的设备。
- 本机是否属于移除目标。
- 应用变化后受影响的设备关系。
- 保留现有设备组后会进入不一致状态的设备关系。
- 每台相关设备的在线情况、成员资格、设备组一致性和版本兼容情况。
- 当前是否存在无法验证且需要安全恢复的情况。
- 当前允许用户执行的动作，以及动作不可用的稳定原因。

产品需要设备名称时，Engine 必须保证产品能用上述稳定设备标识从同一份可信设备资料中取得名称；不能要求产品根据网络消息或临时连接猜测身份。

### 用户决定

Engine 必须支持产品提交当前变化编号和用户选择，并满足：

- 只接受当前仍可决定的变化。
- 接受与保留现有设备组都有明确、可区分的完成结果。
- 重复提交安全，不产生第二项变化。
- 决定在重启和离线后保留。
- 状态已经变化时返回稳定结果，让产品重新加载，而不是应用到错误对象。

### 设备关系结果

Engine 必须按设备提供产品可用的关系事实，至少区分：

- 正常一致。
- 等待本机决定。
- 设备组不一致并已暂停同步。
- 对方版本过旧并已暂停同步。
- 资料无法验证。
- 本机或对方已被当前设备组移除。

这些事实必须与在线/离线分开，产品不得从一个总状态反推其他维度。

### 状态变化提醒

Engine 必须在以下事实发生变化时提醒产品重新读取完整结果：

- 新的用户决定出现或消失。
- 用户决定完成。
- 设备组一致性改变。
- 设备首次被明确判定需要更新，或更新后恢复兼容。
- 本机成员资格改变。
- 无法验证状态出现或解除。

提醒可以合并，但不能成为唯一事实来源。

### 恢复能力

在 PRD 的恢复方向通过评审后，Engine 团队需要提供：

- 从用户选择的可信本机状态开始恢复共同设备组的能力。
- 明确列出会保留、停止使用或需要重新加入的设备。
- 恢复前预览和恢复后完整结果。
- 中断、重启和重复操作下的稳定行为。
- 不自动合并分歧期间内容的保证。

如果 Engine 当前无法提供该恢复能力，产品不能把“恢复到同一设备组”作为已可用动作发布。

## 桌面端能力需求

PRD 通过且 Engine 能力确定后，桌面端需要：

- 在设备页提供持续任务区域、设备级状态和结果导向动作。
- 在应用后台时发送去重后的系统通知。
- 在启动、恢复前台、实时提醒和用户动作完成后读取完整状态。
- 不缓存第二份设备决定队列，不推断来源、影响范围或完成状态。
- 为应用变化、保留现有设备组、重新加入和恢复共同设备组分别提供清晰流程。
- 保持中英文文案及桌面平台行为一致。

## 验收场景

### 正常与离线

1. 普通设备离线后只显示离线，不出现信任警告或系统通知。
2. 设备重新上线且成员关系一致时自动恢复，不要求用户操作。
3. 新设备的安全增加可以自动补齐，不出现破坏性确认。

### 本机移除设备

4. 用户移除丢失设备时，在确认前看见目标和重新加入后果。
5. 提交成功后本机立即停止与目标分享新内容，但不谎称所有离线设备已经完成。
6. 用户关闭窗口后，后台继续处理，重新打开仍显示真实结果。

### 收到设备变化

7. 其他设备提出移除时，本机只收到一次通知，设备页任务持续存在。
8. 确认区域准确显示提出变化的设备、目标设备和两个选择的影响。
9. 用户稍后处理或重启应用，任务不丢失，也不会被自动接受。
10. 本机是目标时，应用变化前出现第二次明确确认。

### 保留与分歧

11. 用户保留当前设备组后，相关设备显示“设备组不一致”，不显示成离线或连接失败。
12. 不一致设备之间不再分享新内容；同一设备组内其他设备继续正常使用。
13. 页面提供真实可执行的恢复入口，或明确说明当前只能从可信设备重新建立设备组；不显示无效重试。

### 版本与验证

14. 只有后台明确确认版本过旧的设备才显示“需要更新”；普通超时和离线不触发该提示。
15. 对方更新后自动重新检查并恢复，不要求重新配对。
16. 资料无法验证时停止相关同步并显示安全恢复说明，不展示内部错误。

### 一致性与隐私

17. 状态提醒丢失、窗口晚打开或后台服务重启后，页面仍能通过完整查询恢复正确状态。
18. 重复点击决定按钮不会重复应用变化。
19. 页面、通知、日志和分析事件均不包含成员历史、签名、密钥、网络地址或剪贴板内容。
20. 桌面、移动端对相同事实使用相同含义；平台限制只影响通知和页面形式，不改变决定结果。

## 成功指标

上线后重点观察以下不含设备身份的产品指标：

- 新设备变化出现后，用户完成决定的比例和耗时区间。
- 用户决定后成功恢复正常同步的比例。
- “设备组不一致”持续超过七天的比例。
- 版本过旧提示后恢复兼容的比例。
- 用户在成员关系任务期间重复移除、重复配对或重置 Space 的比例。

这些指标用于判断流程是否让用户看懂并完成任务，不用于评价用户选择了应用还是保留。

## 待产品评审

1. **恢复方向：** 是否确认统一采用“从可信设备建立新的共同设备组并重新邀请”作为设备组不一致后的恢复方式？
2. **长期分歧：** 是否允许用户无限期保留两个设备组，还是在设备页持续建议恢复但不强制？草案建议允许继续使用，并持续提供恢复入口。
3. **系统通知：** 是否确认每项新决定只通知一次，本机被移除和首次确认需要更新也通知一次？
4. **本地历史：** 本机被移除后，是否允许继续只读访问已经保存在本机的剪贴板历史？需要结合现有加密与产品安全边界确认。
5. **恢复预览：** 恢复共同设备组前，是否要求列出每台设备将“保留、重新邀请或停止使用”的结果？草案建议要求。
