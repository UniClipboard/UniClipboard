# 桌面端主动刷新共享设备规格

## 文档状态

- 状态：可实施
- 日期：2026-08-07
- 适用范围：桌面端设备页、桌面后台接口、Engine 版本接入
- 产品依据：[主动刷新共享设备 PRD](../product/2026-08-07-shared-device-refresh-prd.md)

## 问题陈述

新设备加入某个 Space 后，可能只认识直接与它完成配对的设备，而不知道该 Space 中已经与其他设备建立关系的成员。用户目前没有一个明确入口来主动补全这些设备关系，也无法知道发现、确认和连接分别进行到了哪一步。

这会产生两个问题：

1. 用户看到自己已经加入同一 Space，却仍需等待不透明的后台收敛，无法主动触发一次完整查询。
2. 产品端若只做在线探测或重新加载现有设备列表，会给用户造成“已经刷新”的错觉，但不会发现未知设备。

本功能必须明确解决设备关系补全，不得被实现为剪贴板同步、在线状态探测或网络恢复的别名。

## 解决方案

在设备页“已配对设备”标题右侧增加“刷新共享设备”入口。用户点击后，桌面端向后台发起一次刷新，并立即打开结果窗口。Engine 向当前 Space 中可信的已配对设备查询候选设备，逐台完成本机确认，复用已有成员关系收敛流程保存成功结果和处理后续重试。

产品端只负责以下动作：

1. 发起刷新并保存本轮请求编号。
2. 按请求编号读取完整当前结果。
3. 收到状态变化、连接恢复或事件补刷提醒后，再次读取完整结果。
4. 展示 Engine 给出的阶段和逐台状态。

产品端不得自行查询来源、拼接确认步骤、保存关系、驱动单台重试或推断连接成功。只有 Engine 返回“已连接”，才表示该候选已通过确认并完成保存；设备页列表仍以现有已配对设备列表为唯一依据。

## 用户故事

1. 作为至少拥有一台已配对设备的用户，我希望在设备页看到刷新入口，以便主动补全同一 Space 中的设备关系。
2. 作为尚无已配对设备的用户，我不希望看到一个无法工作的刷新入口，以免误以为产品能从无来源发现设备。
3. 作为发起刷新的用户，我希望点击后立即开始并看到进度，而不需要确认、选择设备或输入信息。
4. 作为发起刷新的用户，我希望只看到已经被实际发现的设备，而不是尚未得到后台确认的预测名单。
5. 作为等待结果的用户，我希望每台设备只显示一行，并在原位置更新状态，以便清楚跟踪变化。
6. 作为等待结果的用户，我希望“已发现”“正在自动连接”和“已自动连接”有严格区别，以免把准备连接误认为连接成功。
7. 作为已有完整设备关系的用户，我希望已存在的设备被明确标记为“已在本机设备中”，且不会重复建立关系。
8. 作为存在离线设备的用户，我希望看到“等待设备上线，会继续尝试”，并在设备上线后自动完成，而不需要再次点击。
9. 作为需要等待安全资料更新的用户，我希望看到“等待资料更新，会继续尝试”，而不是一个无法理解的错误。
10. 作为遇到旧版本设备的用户，我希望看到“版本不兼容”，且该设备不会被误报为已连接。
11. 作为遇到身份或资料校验失败的用户，我希望看到“无法连接”，且该设备不会进入本机设备列表。
12. 作为部分已配对设备暂时不可用的用户，我希望其他来源继续处理，并只看到不暴露设备和底层原因的汇总提示。
13. 作为暂时不想看进度的用户，我希望关闭结果窗口后后台仍继续工作。
14. 作为在刷新过程中再次点击入口的用户，我希望重新看到同一轮最新结果，而不是产生重复查询或重复连接。
15. 作为完成首轮查询的用户，我希望结果窗口保留完整结果并由我手动关闭，而不是自动消失。
16. 作为没有发现新设备的用户，我希望看到明确的“未发现可自动连接的设备”，而不是停留在空白或加载状态。
17. 作为在事件延迟、窗口晚打开或应用恢复前台后查看结果的用户，我希望看到后台当前完整事实，而不是前端拼接出的残缺过程。
18. 作为后台服务刚刚重启的用户，我希望旧进度被明确标记为已结束，并能关闭窗口后重新发起。
19. 作为重视隐私的用户，我希望界面、错误和日志都不暴露地址、身份指纹、安全资料、网络错误原文或任何剪贴板内容。
20. 作为只允许 P2P 的用户，我希望候选暂时不可达时继续等待，而不是自动改用其他传输方式。

## 实现决策

### 1. 责任与数据权威

- Engine 的成员关系收敛流程是设备发现、候选确认、可信关系保存和后续重试的唯一负责人。
- 桌面后台只把 Engine 的发起、查询和状态变化能力转换为本机接口，不保存第二份刷新状态，也不解释内部失败。
- 前端保存的请求编号和结果快照只用于展示；每次完整查询结果都直接替换旧快照，不合并零散过程消息。
- 已配对设备列表继续由现有设备列表接口和设备变化事件负责。刷新结果中的“已连接”不能被前端直接插入设备列表。
- 现有在线探测、网络恢复和成员收敛汇总都不能作为本功能的替代入口或兼容回退。

### 2. 交付顺序

1. 桌面端先采用包含“发起刷新”“查询刷新”和“刷新状态变化”公开能力的 Engine 固定版本。
2. 桌面后台增加对应的本机接口、公开数据结构和状态变化主题，并更新自动生成的客户端契约。
3. 前端增加独立的刷新调用层和结果窗口，再把入口接入设备页。
4. 最后补齐三设备端到端验收，确认状态展示和设备列表更新来自真实连接结果。

不保留旧 Engine 兼容分支，不增加功能开关，也不使用旧接口拼装临时方案。

### 3. 后台接口契约

#### 发起刷新

- 方法与路径：`POST /member/shared-device-refresh`
- 请求体：无
- 成功结果：返回本轮 `requestId`
- 重复发起：当同一 Space 的首轮查询仍在进行时，返回同一个 `requestId`，不得启动第二轮。
- 失败：后台未就绪或 Engine 拒绝开始时，返回稳定错误类别；响应不得包含底层错误原文。

#### 查询完整结果

- 方法与路径：`GET /member/shared-device-refresh/{requestId}`
- 成功结果：返回该请求当前的完整快照。
- 请求不存在：返回 `404` 和稳定错误类别 `shared_device_refresh_not_found`。
- 后台未就绪：返回 `503` 和稳定错误类别 `shared_device_refresh_unavailable`。
- 其他内部失败：返回通用内部错误，不回传 Engine 或网络错误原文。

#### 状态变化提醒

- 实时主题：`shared-device-refresh`
- 事件名称：`shared-device-refresh.changed`
- 事件内容：只包含 `requestId`。
- 前端收到提醒后必须重新查询完整快照，不得把提醒当作状态增量。
- 实时连接重新建立或收到全局“需要补刷”提醒时，只要前端仍持有当前 `requestId`，就必须重新查询该请求。

### 4. 完整结果结构

完整结果包含以下字段：

| 字段 | 含义 |
| --- | --- |
| `requestId` | 本轮刷新编号。 |
| `phase` | 当前阶段：`started`、`discovering`、`connecting`、`round_completed`。 |
| `devices` | 按 Engine 提供的稳定顺序排列、按稳定设备标识去重的完整设备结果。 |
| `totalCount` | 当前结果中的设备总数。 |
| `discoveredCount` | 当前处于已发现状态的数量。 |
| `connectingCount` | 当前处于连接中状态的数量。 |
| `connectedCount` | 已完成连接的数量。 |
| `alreadyPresentCount` | 本机原本已存在的数量。 |
| `waitingForPeerCount` | 等待设备上线的数量。 |
| `waitingForUpdateCount` | 等待资料更新的数量。 |
| `versionIncompatibleCount` | 版本不兼容的数量。 |
| `rejectedCount` | 校验未通过的数量。 |
| `unavailableSourceCount` | 本轮无法回答查询的来源数量；前端只把它解释为“是否存在不可用来源”，不展示数量或来源。 |

每个设备结果只包含：

| 字段 | 含义 |
| --- | --- |
| `deviceId` | 稳定设备标识，仅用于去重、行标识和结果关联，不默认向用户展示完整值。 |
| `displayName` | 设备名称；为空时显示通用的“未命名设备”。 |
| `state` | 当前稳定状态。 |

所有数量必须与 `devices` 中的当前状态一致；前端不得自行修正矛盾数据。若契约不一致，应保留最后一份有效快照并记录脱敏诊断。

### 5. 请求阶段与生命周期

| 阶段 | 产品含义 | 窗口行为 |
| --- | --- | --- |
| `started` | 刷新已被接受，尚未取得候选。 | 显示“正在查找可连接设备”。 |
| `discovering` | 正在向可信来源查询候选。 | 保持查找状态；发现设备后逐行加入。 |
| `connecting` | 至少一个候选正在由 Engine 确认。 | 展示完整设备列表和逐台状态。 |
| `round_completed` | 本轮查询和即时确认已经结束。 | 显示“本轮查找完成”，保留所有结果，不自动关闭。 |

`round_completed` 只表示首轮结束，不表示所有设备都已连接。处于等待状态的设备仍由 Engine 已有收敛流程继续处理，后续变化仍可更新同一请求快照。

同一 Space 仅在首轮仍处于 `started`、`discovering` 或 `connecting` 时复用进行中的请求。首轮完成后，用户再次点击可以开始新一轮；取得新请求编号后，新请求替换旧请求成为当前窗口的数据来源。

刷新请求本身不持久化。后台服务重启后，旧 `requestId` 查询结果为不存在；已经加密保存的候选和重试仍由 Engine 原有收敛机制处理。用户关闭结束提示后，可从入口发起新一轮。

### 6. 单台设备状态

| 后台状态 | 窗口文案 | 规则 |
| --- | --- | --- |
| `discovered` | 已发现，正在准备连接 | 只在真正收到候选后出现。 |
| `connecting` | 正在自动连接 | 正在完成本机直接确认和保存。 |
| `connected` | 已自动连接 | 唯一能表示本轮新连接成功的状态。 |
| `already_present` | 已在本机设备中 | 不重复建立关系。 |
| `waiting_for_peer` | 等待设备上线，会继续尝试 | 首轮可完成，后台继续处理。 |
| `waiting_for_update` | 等待资料更新，会继续尝试 | 首轮可完成，后台继续处理。 |
| `version_incompatible` | 版本不兼容 | 当前不能进入设备列表；设备升级后可由后台继续推进。 |
| `rejected` | 无法连接 | 不展示具体校验原因，不留下部分正式关系。 |

同一设备只保留一行并按 `deviceId` 更新。前端严格保留后台给出的数组顺序，不按名称、状态或到达时间重新排序。

### 7. 设备查询与安全确认

- 查询来源仅限当前 Space 中已经配对且仍可信的设备。
- 来源返回的只是候选资料，不能直接成为本机可信关系。
- Engine 必须直接确认候选的 Space、身份、安全历史、准入状态和协议兼容性；来源设备的声明不能替代候选自身证明。
- 只有确认和持久化全部成功后，状态才能进入 `connected`。
- 候选确认失败时不得写入部分成员关系、可信关系或地址资料。
- 超过单批上限的来源结果必须使用稳定游标完整读取，不能静默遗漏后续设备。
- 候选去重、冲突处理和重试全部复用 Engine 现有成员关系收敛机制，不增加第二套队列或名单。

### 8. 设备页与结果窗口

- 入口位于“已配对设备”标题右侧，使用刷新图标，悬浮说明为“刷新共享设备”。
- 至少存在一台已配对设备时显示入口；没有来源时完全隐藏。
- 首轮进行中时图标显示进行中状态但保持可点击；再次点击只重新打开当前窗口。
- 点击入口不出现确认步骤。前端立即打开窗口、显示“正在查找可连接设备”并发起请求；取得请求编号后立即查询完整结果。发起失败时关闭进度窗口，保持设备页内容不变，并提示“暂时无法开始刷新”。
- 窗口可以通过关闭图标、Esc 或点击外部关闭。关闭只影响展示，不向后台发送取消动作。
- 窗口不提供取消、设备选择、单台重试或手动确认操作。
- 结果为空且首轮已完成时，显示“未发现可自动连接的设备”。
- `unavailableSourceCount` 大于零时，同时显示“部分已配对设备目前不可用”；不显示来源名称、数量或原因。
- 窗口关闭后，刷新状态变化不发送系统通知。
- 任一设备首次变为 `connected` 时，前端重新读取现有已配对设备列表；不得直接用刷新结果构造设备卡片。若设备变化事件先到达，则以同一权威列表自然更新。

### 9. 前端一致性与竞态处理

- 发起成功取得 `requestId` 后立即查询一次完整结果，以覆盖“开始”提醒早于前端保存编号的情况。
- 同一请求同一时间只允许一个结果查询在途。查询期间收到新的提醒时，只记录“需要再查一次”，当前查询结束后立即补查，避免旧响应覆盖新状态。
- 只有与当前 `requestId` 相同的提醒和查询结果可以更新窗口；旧请求的迟到结果必须忽略。
- 查询成功时整份替换窗口快照。不得逐项合并，也不得根据计数推断某台设备状态。
- 暂时查询失败时保留最后一份有效快照，并显示“暂时无法更新刷新状态”；下一次状态提醒或实时连接恢复时继续查询。
- 查询返回不存在时，窗口显示“刷新状态已结束，请重新刷新”。窗口不提供内嵌重试；用户关闭后从入口重新发起。

### 10. 隐私、持久化与诊断

- 本功能不新增桌面端持久化状态、明文缓存、临时明文文件或第二份设备名单。
- 候选、成员、可信关系、地址和重试继续由 Engine 通过已有加密存储和原子保存流程管理。
- 界面和公开错误只允许出现设备名称、经过产品处理的稳定设备标识、请求阶段、数量和本规格定义的状态。
- 界面、接口错误和日志不得包含剪贴板内容、文件资料、网络地址、身份指纹、签名、安全资料或底层错误原文。
- 日志允许记录请求编号、阶段、聚合数量、耗时和稳定失败类别。涉及单台设备时只能记录请求内生成的脱敏序号，不记录设备名称或稳定设备标识。
- 本规格不新增用户行为分析事件；如未来需要，必须另行定义隐私审查和稳定事件名。

## 测试决策

### 测试原则

- 测试外部可观察行为，不验证私有函数、内部队列或具体重试次数。
- “已连接”的验收必须同时看到 Engine 返回 `connected` 和权威已配对设备列表包含目标设备，不能以发起成功、事件已发送或连接尝试计数代替。
- 异步场景使用有截止时间的状态查询，不使用固定等待时间断言成功。
- 安全场景验证候选最终未进入设备列表，并验证公开结果和日志已脱敏；不依赖内部错误字符串。

### 主要测试层级

1. Engine 端到端测试：用三个真实 Engine 实例覆盖 A 已认识 C、B 只认识 A、B 发起刷新后发现并连接 C；再覆盖 C 离线后恢复、分页、重复发起、来源部分不可用、冲突候选和版本不兼容。
2. 桌面后台契约测试：验证发起与查询操作被原样交给 Engine，完整快照字段无损映射，未知请求返回稳定 `404`，状态变化只发送请求编号，所有错误均不泄露底层内容。
3. 设备页行为测试：验证入口显隐、首轮进行中重复点击复用请求、完整快照替换、设备行稳定更新、所有文案映射、关闭窗口后后台继续、重连补查、旧响应不覆盖新结果，以及连接成功后重新读取权威设备列表。
4. 桌面三实例验收：从设备页实际发起刷新，观察 C 从“已发现”进入“已自动连接”，确认 C 出现在 B 的已配对设备列表；关闭窗口和离线恢复场景也必须通过。

### 必须通过的验收场景

1. A 已与 C 建立关系，B 新与 A 配对。B 点击刷新后先看到 C 被发现，随后看到“已自动连接”，且 C 出现在 B 的已配对设备列表。
2. C 离线时，B 显示“等待设备上线，会继续尝试”；C 恢复后自动连接，不要求 B 再次点击。
3. 刷新中关闭窗口，后台继续；连接成功后设备列表更新，且不出现系统通知。
4. 首轮进行中连续或并发点击入口，只存在一个请求编号、一份结果窗口和一轮后台查询。
5. 没有新设备时显示明确空结果；已存在、版本不兼容和拒绝状态都不会被误报为“已自动连接”。
6. 某个查询来源不可用时，其他来源继续；窗口只出现汇总提示，不暴露来源和错误原文。
7. 状态提醒延迟、漏收、窗口晚打开或实时连接恢复后，重新查询得到的设备和状态与 Engine 当前结果一致。
8. 后台重启后，仍打开的窗口显示“刷新状态已结束，请重新刷新”；关闭后可以开始新一轮。
9. 不同 Space、身份冲突、资料篡改或确认失败的候选不会进入设备列表，也不会留下部分正式关系。
10. 所有界面、接口错误、日志和测试证据均不包含剪贴板内容、网络地址、身份指纹、签名、安全资料或底层错误原文。

## 不在范围内

- 刷新过程不传输剪贴板、历史、文件或任何最新内容。
- 在线状态探测、网络恢复或连接通道切换。
- 用户选择设备、逐台确认、输入邀请码或其他资料。
- 取消正在进行的刷新。
- 手动重试单台设备。
- 因 P2P 不可达自动改用 LAN 或其他传输方式。
- 系统通知、完成提醒或后台弹窗。
- 长期保存刷新请求和窗口进度。
- 修改已有成员关系收敛的信任模型、重试策略或持久化格式。
- 为旧 Engine、旧桌面后台接口或旧前端保留兼容层。

## 补充说明

- 本规格描述的是桌面端对既有 Engine 能力的完整接入，不在桌面仓重新实现 Engine 内部的候选、信任、加密存储或重试逻辑。
- “刷新共享设备”与移动端可能存在的“刷新内容”语义不同。本入口只补全设备关系，任何剪贴板内容传输都必须继续由独立的同步动作负责。
- 实施完成的判定以三设备真实流程、权威设备列表和隐私检查共同通过为准，单独完成界面、后台接口或 Engine 版本更新都不算交付完成。
