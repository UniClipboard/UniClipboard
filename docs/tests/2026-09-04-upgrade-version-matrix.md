# 0.20 与 1.0 alpha 升级版本矩阵

## 目标

长期保存少量但能代表真实破坏边界的旧版开发资料，持续验证这些资料可以原地升级到当前版本。矩阵按持久数据、密钥、设备关系和目录布局变化选择，不为每个补丁或预发布版本重复保存相同状态。

## 选定版本

| 来源版本 | 代表边界 | 样本场景 |
| --- | --- | --- |
| `v0.19.1` | 稳定旧版与当前升级策略的最低基线 | 单机已初始化、无用户内容 |
| `v0.20.0-alpha.2` | 独立 Engine 切换前，旧网络身份目录 | 单机已初始化、无用户内容 |
| `v0.20.0-alpha.6` | 自动安全升级与持久 legacy bootstrap，网络身份转入文件密钥 | 单机已初始化、无用户内容 |
| `v1.0.0-alpha.4` | workspace convergence、设备信任选择、旧版成员交接和 `daemon.conn` | 单机已初始化、无用户内容 |

## 未选版本

- `v0.20.0-alpha.1/.3/.4/.5`：其边界已分别由 alpha.2 和 alpha.6 两端覆盖。
- `v1.0.0-alpha.1/.2/.3`：alpha.4 覆盖其后的成员关系重写边界。
- `v1.0.0-alpha.5`：没有新的持久格式；仅在后续增加“已移除设备等待重新批准”多机场景时采用。
- `v1.0.0-alpha.6/.7`：没有正式桌面发布资产，不能作为官方旧版输入。

## 验收

每个来源版本必须满足：

1. 官方 Apple Silicon 发布程序和 `SHA256SUMS.txt` 通过固定摘要校验。
2. 旧版只在随机 `dev-upgrade-*` 档案中运行，并使用开发文件密钥。
3. 样本只包含白名单内的数据库、WAL、设置、开发密钥、网络身份和缓存。
4. 使用统计关闭，不包含日志、令牌、锁、进程文件、本机绝对路径或真实用户内容。
5. 压缩包和逐文件摘要正确，任意修改都会被拒绝。
6. 当前开发版能从样本启动，本机成员状态为活动，成员列表只有本机。
7. 升级后明确要求重新配对，不得自动继承旧设备组。
8. 两台旧设备升级后都先只保留本机；其中一台离线后稍晚升级也不能自动恢复关系。
9. 用户确认原空间口令并重新邀请后，两台设备恢复双向同步，重新配对提示立即清除且重启后不再出现。
10. 桌面窗口必须真实显示升级提示；完成重新配对后，两边都在 30 秒内显示成功，不需要刷新。

当前仓库样本只覆盖 macOS Apple Silicon。Windows、Linux 和 macOS Intel 必须使用各自官方程序生成独立目录后才能记为覆盖。

## 已发现并修复的问题

`v1.0.0-alpha.4` 已经删除三张退役的旧关系表，但保留了对应迁移记录。V3 存储升级曾错误要求这些表必须存在，导致合法资料被判为损坏。当前规则只允许这三张已退役表缺失；未知表或其他必需表缺失仍然拒绝升级。

启动时的重新配对提示原本可能在窗口仍隐藏时开始动画，并长期停留在透明状态。现在该启动提示直接显示，不再依赖入场动画。添加设备成功后的反馈从 2 秒延长到 5 秒，让用户有足够时间确认结果。

## 恢复策略

所有选定版本统一采用 `v0.19.1` 的恢复方式。升级只保留本机资料和身份，旧设备关系全部作废；用户必须选定一台保留设备、确认原空间口令并生成新邀请，再让其他升级设备逐台加入。离线设备回来后执行同样流程，已移除设备不会自动重新获得资格。
