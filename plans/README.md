# 四平台 P2P 核心实施计划

本计划由 2026-07-19 的架构评估生成，基于提交 `1c229e9e1`。目标是让桌面、HarmonyOS、Android、iOS 使用同一套完整 P2P 核心，并在验证稳定后迁入一个独立的 `UniClipboardCore` 仓库。

执行者开始前必须完整阅读对应计划，逐项运行验证命令。任何计划触发停止条件时，不得用现有 LAN HTTP 移动方案代替完成。

## 执行顺序与状态

| 计划 | 标题                                   | 优先级 | 工作量 | 依赖 | 状态        |
| ---- | -------------------------------------- | ------ | ------ | ---- | ----------- |
| 001  | 固化四平台完整 P2P 产品与架构决策      | P0     | S      | -    | DONE        |
| 002  | 证明完整节点可在四个平台构建并反复启停 | P0     | L      | 001  | IN PROGRESS |

状态值：`TODO`、`IN PROGRESS`、`DONE`、`BLOCKED`、`REJECTED`。

## 依赖说明

- 002 必须在 001 后执行，因为执行 001 前，`VISION.md` 和移动研究文档仍把 LAN HTTP 写成锁定方案。
- 003 必须在 002 后执行，因为 iOS、Android 的完整依赖图当前仍有明确的移动目标编译失败，且节点不能在同一进程反复启动。
- 004 必须在 003 后执行，避免 Swift、Kotlin、ArkTS 分别复制内部装配和连接恢复逻辑。
- 005 必须在四平台真机互通后执行；先拆仓会把尚未稳定的跨平台改造变成跨仓协调问题。

## 统一完成标准

- 四个平台使用同一空间身份、同一加密与持久化规则、同一配对协议、同一剪贴板与文件传输协议。
- “对等节点”不等于“永久后台在线”。移动系统暂停应用时节点可离线；恢复后必须以原身份重新成为完整节点。
- 所有持久化业务负载保持密文。平台只能提供私有目录、安全密钥库、剪贴板和文件句柄，不能自行持久化明文业务内容。
- 正式构建中每个平台只能有一个核心路径。旧 LAN HTTP 只允许在迁移窗口内存在；iOS 和 Android 首个纯 P2P 稳定版发布时，必须在计划 005 中登记不可滚动后移的明确删除版本。
- 一个 `core-vX.Y.Z` 发布同时生成 Rust 源码、iOS、Android、HarmonyOS 产物及校验信息。

## 已考虑但否决

- 一个 crate 一个仓库：相关改动需要跨仓同步，维护成本高于收益。
- 直接公开现有 `uc-core`：公开范围过大，且调用方仍需理解 `uc-application`、`uc-infra`、`uc-bootstrap`。
- 直接搬现有九个 crate：当前移动目标尚未通过，定制 `iroh-blobs` 也没有独立交付。
- 继续以 LAN HTTP 作为 Android/iOS 主方案：不满足四个平台都是完整 P2P 节点的目标。
