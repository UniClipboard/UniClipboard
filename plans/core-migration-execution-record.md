## 固定决定

### 产品与运行方式

- desktop、iOS、Android 和未来的 HarmonyOS 产品应用使用同一套完整 P2P 核心、身份、配对、加密、内容和传输规则。
- 移动系统暂停应用时，节点正常离线；恢复后使用原身份重新上线。项目不承诺移动端永久后台在线。
- LAN HTTP 是用户明确选择的独立兼容通道，不是 P2P 失败后的自动回退，也不能替代 P2P 验收。
- 离线发送失败后不自动补投，仍由用户主动重发。

### 核心边界

- `uc-engine` 是 Rust 调用方唯一稳定入口；内部 crate 不单独承诺稳定接口。
- 平台只提供私有目录、安全存储、剪贴板、文件句柄和生命周期能力，不拥有数据库、网络协议、加密格式或业务持久化规则。
- 文件内容本体允许按原始字节落盘；文件名、路径、标题、预览、标签和其他业务内容仍必须加密。
- desktop 的正式业务只通过 `uc-engine` 使用核心；LAN 兼容实现保持显式开启和独立边界。

### 仓库与发布

- `UniClipboard/core` 是核心源码、数据库迁移、移动绑定和统一核心发布的唯一目标事实来源。
- desktop 仓保留 daemon、CLI、Web 服务、Tauri、桌面平台接入和 LAN 兼容产品入口。
- Android 和 iOS 只消费固定核心版本及其校验信息，不跟踪生成绑定或核心二进制副本。
- 一个 `core-v*` 发布的所有平台文件必须来自同一提交，并由同一清单记录版本、来源、架构和校验值。
- 版本从 `0.20.0-rc.1` 单调前进；稳定版本应为 `0.20.0`，不能回退到原计划中的 `0.1.0`。

## 执行结果

### Plan 001：统一方向

2026-07-19 完成产品和架构文档收敛。当前只有“四平台完整 P2P”一个方向，旧的“移动端只使用 LAN HTTP”方案被保留为独立兼容通道说明，不再是未来核心架构。

### Plan 002：证明跨平台可行性

已完成的主要证据：

- 定制网络依赖可以从固定来源独立解析，iOS 与 Android 使用相同网络和 blob 依赖。
- 生产形态的 `Engine` 在同一进程内连续启动和关闭十次，网络身份保持不变。
- iOS 最小宿主已在实体设备构建、签名、安装和启动，并完成与 desktop 的内容流程和落盘检查。
- Android 14 ARM64 模拟器已与 desktop 完成真实 P2P 配对、双向文本、图片、文件、中继传输、五轮暂停恢复和进程结束后的身份恢复。
- Android 模拟器接收文件的字节数和 SHA-256 与发送端一致。
- Android 模拟器私有数据、缓存和临时目录的扫描覆盖 15 个文件、约 1.3 MB；测试正文、文件名和路径均无明文命中，允许的原始文件内容除外。

没有完成的证据：

- Android 和 HarmonyOS 实体设备的网络切换、后台策略、硬件安全存储和内容矩阵。
- 四个平台全部设备对的双向互通。
- 覆盖所有实体移动设备目录、文件名、路径、标签和预览的完整明文扫描。

这些项目由用户在 2026-07-22 决定停止执行，保持未通过。

### Plan 003：建立唯一核心入口

已完成 `uc-engine` 的公开约定、生命周期、生产会话、操作路由、业务处理、长期任务和组装职责拆分。外部调用不再依赖 `internal`、`AppFacade` 或 `CliAppRuntime`，desktop daemon 的生产路径只使用 `uc-engine`。

随后完成了结构复核：

- `internal` 已收回为私有实现，workspace 其他包不再引用它。
- LAN 兼容能力和开发工具与完整 P2P 主路径分离。
- desktop 保留项目不再直接依赖准备迁出的核心内部包。
- 公开接口、宿主接入、运行行为和移动绑定检查回到各自拥有者。
- Plan 003 的接口测试、双节点测试、全项目编译和入口检查均已通过。

### Plan 004：交付移动绑定

已完成 iOS、Android 共用 UniFFI 绑定和 HarmonyOS N-API 薄绑定，覆盖生命周期、状态事件、配对、文本、图片、文件、系统剪贴板、安全存储和文件句柄。

验证结果包括：

- iOS 和 Android 共用绑定可独立构建，并由各自产品应用接入统一核心状态与空间创建、加入流程。
- HarmonyOS ARM64 HAP 在 DevEco 模拟器中完成构建、签名、安装和启动，原生模块可加载并报告就绪。
- iOS、Android、HarmonyOS 的系统安全存储、文件出口和暂停恢复规则已接入。
- 三个平台的发布文件可以从同一核心提交生成，错误版本的绑定和本地库会在正式构建前被拒绝。

HarmonyOS 模拟器只证明构建和原生模块加载，不等于实体设备或产品应用验收。六种设备对的实体设备矩阵没有执行，因此 Plan 004 不能标记完成。

### Plan 005：迁入独立核心仓库

#### Phase 0 至 Phase 3：边界、检查和建仓

- desktop 先建立依赖防火墙、公开入口检查、绑定来源检查、持久化检查和 LAN 自动回退检查。
- 代表性的本地路径、错误绑定来源和自动回退配置均能被检查准确拒绝。
- 建仓基线为 desktop 提交 `12104cbab7a3b167f33f95c5a9d6d7d90fbbfa75`。
- 使用 `git-filter-repo 2.47.0` 保留 348 个相关提交，并保存旧提交到新提交的历史映射。
- 公开仓库最终命名为 `UniClipboard/core`，默认分支为 `main`，保护规则恢复为至少一次批准、最新检查通过、讨论解决、线性历史、禁止强推和禁止删除。
- 独立仓完成锁定依赖解析、全项目全部目标编译、格式、仓库边界和 Git 完整性检查。

#### Phase 4：候选版本

- 候选版本确定为 `core-v0.20.0-rc.1`，对应提交 `dcdccb234f020be49884bf92d886f25a0f192188`。
- 两次有效发布演练 `30054432143` 和 `30057385020` 均成功。稳定字段一致；可逐字节复现的 13 个文件完全一致，重新封装的 9 个文件分别由清单记录并校验。
- 正式预发布运行 `30058537116` 成功，GitHub Release 包含清单和 22 个声明文件；名称、大小和 SHA-256 全部核对一致。
- 发布清单如实把 iOS、Android 和 HarmonyOS 实体设备状态记录为 `skipped`。

#### Phase 5：desktop 切换

- desktop 迁移提交为 `db198c2951ede17104695e6c30c4ffa10f7dc9f8`，已推送到迁移分支。
- 11 个迁出包、对应数据库迁移、绑定脚本和旧移动核心发布流程已从 desktop 删除。
- desktop 闭包中的 7 个核心包只来自候选提交 `dcdccb234f020be49884bf92d886f25a0f192188`。
- 全新远端检出在旧核心目录完全不存在时，仍可完成锁定依赖解析和消费者边界检查。
- desktop 全项目全部目标编译、daemon、CLI、Tauri 链接和临时资料下的创建空间、启动、健康检查、停止流程均通过。

#### Phase 6：Android 和 iOS 切换

- 移动仓 `main` 已推进到 `d30b91439d17e0e139ee536964a4ce8713a05d7f`。
- Android 和 iOS 固定 `core-v0.20.0-rc.1` 及来源提交 `dcdccb234f020be49884bf92d886f25a0f192188`。
- Android 通过 Release POM 使用 AAR、Kotlin 绑定和运行依赖，ARM64 正式包构建成功且包内只有一份候选核心。
- iOS 同时使用 XCFramework、Swift 绑定和 SwiftPM 校验值，Release 模拟器构建成功，最低系统版本保持 16.4。
- 生成绑定和核心二进制不再由移动仓跟踪，错误 AAR 或 Swift 绑定会在构建前被拒绝。

#### Phase 7：HarmonyOS 消费端不适用

当前没有 HarmonyOS 产品应用或社区应用仓库，只有核心仓中的绑定和验证程序。因此没有真实消费端可迁移，也不得临时创建应用来满足计划。

未来建立 HarmonyOS 产品应用时，应单独制定接入计划，直接消费当时固定的 `core-v*` 发布，不复制核心源码或长期保留消费端补丁。

#### Phase 8：稳定发布和清理

本阶段尚未完成。2026-07-24 的发布前审计得到以下结论：

- `core-v0.20.0-rc.1` 之后，核心 `main` 已增加目录发送状态修复提交 `818530b5ccdb259a36c71333320c024d56c89e27`，因此稳定版不能直接复用候选提交。
- desktop 迁移分支 `34114f0f6` 已与自己的远端同步，但相对 desktop `main` 领先 208 个提交、落后 8 个提交，尚未进入默认分支。
- 这 8 个提交与迁移内容存在删除和修改冲突。基线后的核心行为修复必须先由 `UniClipboard/core` 承接，不能在 desktop 合并时直接丢弃。
- mobile 的候选核心接入已经进入远端 `main`，但稳定发布后仍需更新为最终固定版本。
- 核心、desktop 和 mobile 的本地工作区可能还有其他并行改动；继续 Phase 8 前必须重新核对，不能把本快照当作干净工作区证明。
